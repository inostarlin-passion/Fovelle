## 1. 目的与测试策略

本规格把需求拆解为原子验收标准，并按“单元测试 → 集成测试 → 系统测试”的顺序定义可重复的测试用例。每个用例均固定输入、操作和预期结果；测试命令默认在仓库根目录执行。

“不改文件名、类名、函数名、变量名”解释为：保留既有源文件、类、函数和变量的命名；用户明确要求删除的 Windows/Linux 支持文件是例外，按删除验收。保留 `qview_*.ts`、`qView.icns` 等文件名不等同于保留旧品牌身份。

性能测试采用可审计的启动烟囱负载：运行 `Fovelle --version`。需求没有给出目标负载、机器规格或数值阈值，因此本规格将 1 秒平均响应、2 秒 P99/最大响应、1 次/秒吞吐和 256 MiB 峰值 RSS 作为本次发布前的保守本地门槛；这些门槛只适用于该烟囱负载，不能推导出大图片加载或长时间浏览的性能结论。

## 2. 外部事实、推断与不确定性

### 2.1 可验证事实

| 编号 | 类型 | 事实 | 对实现/测试的影响 |
|---|---|---|---|
| F-01 | 外部事实 | qView 上游仓库将项目描述为重视极简和可用性的图片查看器，并标注 GPL-3.0。来源：[qView GitHub](https://github.com/jurplel/qView) | README 必须明确“基于 qView”和 GPLv3 继承关系，不能把 Fovelle 描述成无来源的新项目。 |
| F-02 | 外部事实 | Apple 将 `CFBundleIdentifier` 定义为 Bundle 的唯一标识，通常采用 reverse-DNS 格式，允许字母、数字、连字符和句点。来源：[Apple CFBundleIdentifier](https://developer.apple.com/documentation/bundleresources/information-property-list/cfbundleidentifier) | 验证 `io.github.inostarlin-passion.Fovelle` 的 Bundle ID 及其在生成 `Info.plist` 中的一致性。 |
| F-03 | 外部事实 | CMake 的 `MACOSX_BUNDLE` 生成 macOS Application Bundle；`MACOSX_BUNDLE_INFO_PLIST` 可指定自定义模板，并可配置 Bundle 名称、版本和 GUI identifier。来源：[CMake MACOSX_BUNDLE_INFO_PLIST](https://cmake.org/cmake/help/latest/prop_tgt/MACOSX_BUNDLE_INFO_PLIST.html)、[CMake MACOSX_BUNDLE](https://cmake.org/cmake/help/latest/prop_tgt/MACOSX_BUNDLE.html) | 验证 CMake 目标类型和 `Info.plist` 元数据，而不只检查源代码文本。 |
| F-04 | 外部事实 | Qt 将 `applicationName`、`organizationName`、`organizationDomain` 和 `applicationVersion` 作为 `QCoreApplication` 身份属性；其中组织属性会影响默认 `QSettings` 位置，应用版本可用于命令行输出。来源：[Qt QCoreApplication](https://doc.qt.io/qt-6/qcoreapplication.html) | 运行时测试同时检查组织名、组织域、应用名和版本，避免只改窗口标题。 |
| F-05 | 外部事实 | GitHub Releases REST API 的 releases 路径为 `/repos/{owner}/{repo}/releases`，发布对象包含 `tag_name`。来源：[GitHub REST API releases](https://docs.github.com/en/rest/releases/releases?apiVersion=latest) | updater 应查询 `inostarlin-passion/Fovelle`，并能处理 `0.1.0` 或 `v0.1.0` 形式的 tag。 |
| F-06 | 外部事实 | Qt macOS 部署文档要求 GUI 应用以 Bundle 形式部署，`macdeployqt` 用于把 Qt 框架和插件放入 Bundle。来源：[Qt macOS Deployment](https://doc.qt.io/qt-6/macos-deployment.html) | `macdeploy.sh` 只操作 `Fovelle.app`，并在系统测试之外单独做 shell 语法/路径审计。 |
| F-07 | 外部事实 | GNU 项目提供 GPLv3 正式文本。来源：[GNU GPL](https://www.gnu.org/licenses/gpl.html) | About、README 和 LICENSE 的交叉检查以 GPLv3 为准。 |

### 2.2 基于仓库的推断

| 编号 | 推断 | 依据 | 风险控制 |
|---|---|---|---|
| I-01 | `https://github.com/inostarlin-passion/Fovelle` 是本项目的目标 GitHub 地址。 | 本地 `origin` remote 返回该地址，当前分支为 `main`。 | 只把该地址用于项目身份、About 和 updater；不声称该远程仓库已有正式 Release。 |
| I-02 | `main` 是本次 CI nightly 的默认分支。 | 本地分支名和工作流 nightly 条件均为 `main`。 | 测试同时检查 workflow 中不存在旧的 `master` nightly 条件。 |
| I-03 | `0.1.0` 是本次 Fovelle 首发版本，内部旧的数值版本兼容宏可以继续为 `0.1`。 | CMake 工程版本为 `0.1.0`，显示层改用完整版本字符串。 | Bundle、CLI、About 和 CMakeCache 均检查完整的 `0.1.0`。 |
| I-04 | 图标文件名和翻译文件名属于用户要求保留的项目结构，不能据此判定旧品牌运行身份仍存在。 | 用户明确禁止修改文件名；源代码已把 Bundle/应用身份改为 Fovelle。 | 静态审计排除 `qView.icns`、`qview_*.ts` 等文件名，只拒绝旧 URL、旧 Bundle、旧平台目标和旧应用路径。 |

### 2.3 不确定性与边界

| 编号 | 不确定性 | 处理方式 |
|---|---|---|
| U-01 | 用户说明目前没有 Fovelle 官网；无法从“没有官网”证明互联网上永远不存在其他页面。 | 只验收 README/About 不设置官网链接，并记录“暂无官网”，不测试一个不存在的 URL。 |
| U-02 | 需求未给出目标图片尺寸、并发用户数、持续时间、CPU/网络/句柄数上限。 | 以 `--version` 启动烟囱负载定义本次保守门槛；长时间图片浏览和正式发布机的 QoS 标为未覆盖。 |
| U-03 | 为保证测试确定性，单元/集成测试关闭在线 updater；在线分支仅做编译验证。 | 不把“能编译”写成“真实 GitHub API 已成功返回”；需要发布前另做带网络的环境测试。 |
| U-04 | 当前开发机没有执行完整 Apple 证书、notarization、DMG 实机分发链路。 | 只验收脚本语法、Bundle 路径和静态参数；签名/notarization 作为发布前剩余项。 |
| U-05 | 直接 CMake Debug 配置未设置 `CMAKE_OSX_DEPLOYMENT_TARGET` 时，生成 plist 的 `LSMinimumSystemVersion` 为空；CI 构建脚本会从 Qt 配置推导该变量。 | 本次把它记录为构建环境边界，不把本地 Debug 的空值误报为 Fovelle 身份失败。 |

## 4. 测试用例

以下每个测试用例都包含测试目的、前置条件、输入数据、操作步骤、预期结果和后置条件。用例 ID 与验收标准一一对应或明确标注覆盖范围。

### 4.1 单元测试

#### U-01 应用身份

- 测试目的：验证 AC-02、AC-03 的 Qt 运行时身份。
- 前置条件：macOS；已配置 `build`；编译选项为 `BUILD_TESTS=ON`、`QV_DISABLE_ONLINE_VERSION_CHECK=ON`。
- 输入数据：组织名 `Fovelle`、组织域 `io.github.inostarlin-passion`、应用名 `Fovelle`、版本 `0.1.0`。
- 操作步骤：执行 `QT_QPA_PLATFORM=cocoa build/tests/actionmanagertests`，观察 `testApplicationIdentity`。
- 预期结果：组织名、组织域、应用名和应用版本逐项相等，测试进程退出码为 0。
- 后置条件：不改变用户设置；测试进程退出。

#### U-02 About 内容

- 测试目的：验证 AC-03、AC-05，确保 About 不因字符串遗漏或旧官网链接回归。
- 前置条件：同 U-01；可创建 `QVAboutDialog` 的 QtTest 进程。
- 输入数据：用户规定的英文 About 文本、GitHub URL、无官网链接。
- 操作步骤：执行同一测试程序，观察 `testAboutDialogIdentity` 对窗口标题、Logo、版本、副标题、About HTML 和 updateLabel 的断言。
- 预期结果：About 窗口标题为 `About Fovelle`；Logo 为 `Fovelle`；副标题为 `version 0.1.0`；About HTML 精确等于规格文本；不含 `interversehq.com`；更新标签为空。
- 后置条件：对话框由测试对象销毁；不产生网络请求。

#### U-03 运行时窗口身份

- 测试目的：验证 AC-12，检查主窗口默认标题不会继续显示 qView。
- 前置条件：同 U-01；Cocoa 平台插件可用。
- 输入数据：未加载图片的 `MainWindow`。
- 操作步骤：执行 `testWindowTitleIdentity`，调用 `updateWindowTitle()` 后读取窗口标题。
- 预期结果：窗口标题为 `Fovelle`，测试通过。
- 后置条件：窗口关闭，ActionManager 克隆对象回收。

#### U-04 单元测试确定性

- 测试目的：验证 AC-14、AC-18，确认测试可以关闭网络并使用固定 Cocoa 平台。
- 前置条件：可重新配置 CMake；网络可用性不应影响测试。
- 输入数据：`-DBUILD_TESTS=ON -DQV_DISABLE_ONLINE_VERSION_CHECK=ON`，CTest 环境 `QT_QPA_PLATFORM=cocoa`。
- 操作步骤：重新配置、构建，然后连续执行两次 `QT_QPA_PLATFORM=cocoa ctest --test-dir build --output-on-failure`。
- 预期结果：两次均为 `1/1` 测试通过；不依赖 GitHub API 返回值。
- 后置条件：保留构建日志和 CTest 输出作为审计证据。
