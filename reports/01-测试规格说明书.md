本规格书覆盖 Release 产物必须满足的四个外部性质：Universal（`arm64`+`x86_64`）、自包含 Qt 运行时、Developer ID Application 签名/强化运行时、Apple notarization ticket 已 staple 且 Gatekeeper 可接受。

## 2. 多跳证据分析

### 2.1 事实

1. [Release run 32113103430](https://github.com/inostarlin-passion/Fovelle/actions/runs/32113103430) 虽然状态为 success，但日志显示 runner 为 `macos-14-arm64`，Configure 没有 `CMAKE_OSX_ARCHITECTURES`，Package 步骤只有 `ditto ... build/Fovelle.app ...zip`。
2. 历史资产 [`Fovelle-v0.1.0-macOS.zip`](https://github.com/inostarlin-passion/Fovelle/releases/download/v0.1.0/Fovelle-v0.1.0-macOS.zip) 解压后的主二进制被本地工具验证为 `Mach-O 64-bit executable arm64`，`lipo -info` 为 thin `arm64`。
3. 同一资产的 `codesign --display --verbose=4` 显示 `flags=... (adhoc,linker-signed)`、没有 `Authority=Developer ID Application`、没有安全时间戳；`spctl` 报告 `code has no resources but signature indicates they must be present`。
4. 历史资产没有 `Contents/Frameworks`；主程序仍依赖 `@rpath/Qt*.framework`。这说明 Release workflow 未执行 `macdeployqt`，产物也不是自包含 Qt app。
5. GitHub Actions Secrets API 只返回名称，不返回值；当前仓库可见五个预期名称：`APPLE_APP_SPECIFIC_PASSWORD`、`APPLE_CERTIFICATE_BASE64`、`APPLE_CERTIFICATE_PASSWORD`、`APPLE_ID`、`APPLE_TEAM_ID`。

### 2.2 推断

最小根因链为：arm64 runner 的默认构建 → 发布 thin app；直接压缩未部署 Qt 的构建目录 → 产物缺少运行时依赖；CMake linker 生成的 ad hoc 签名未被 Developer ID 重签 → 没有 Team ID、时间戳、Hardened Runtime 和 notarization ticket；Gatekeeper 因此拒绝该下载产物。用户看到的“App 已损坏”与该链一致，但“具体弹窗文案由哪一条 Gatekeeper 规则触发”不是日志直接给出的事实。

### 2.3 外部可验证依据与不确定性

- [Qt for macOS 官方文档](https://doc.qt.io/qt-6/macos.html)说明使用 `CMAKE_OSX_ARCHITECTURES="x86_64;arm64"` 构建 Universal binary。
- [CMake `OSX_ARCHITECTURES` 文档](https://cmake.org/cmake/help/latest/prop_tgt/OSX_ARCHITECTURES.html)说明该属性控制 macOS target 的 `-arch` 列表。
- [Apple 分发签名文档](https://developer.apple.com/documentation/xcode/creating-distribution-signed-code-for-the-mac/)要求 Developer ID 分发使用 `--timestamp` 和 Hardened Runtime，并说明签名顺序。
- [Apple 公证文档](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution?changes=_5)要求外部分发 app 使用 Developer ID 签名并通过 notary service，ticket 可 staple 到 app。
- [Apple notarytool 文档](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow)说明使用 `notarytool submit --wait`、`stapler staple` 和 `stapler validate` 的流程。
- [GitHub Secrets 文档](https://docs.github.com/en/actions/concepts/security/secrets)说明 workflow 必须显式将 Secret 作为环境变量或 action input 使用。

远端修复后的 Release 尚未重跑；本地没有执行 Apple notarization，因而不能把本地 dry-run 解释为 Apple 服务已批准。

## 3. 修复设计

1. Release Configure 增加 `-DCMAKE_OSX_ARCHITECTURES="x86_64;arm64"`，并在打包脚本中对 app 内每个 Mach-O 用 `lipo -archs` 强制检查两种架构。
2. 运行 `macdeployqt`，将 Qt framework、platform plugin 和 image plugin 部署到 app 内，再进行架构和签名检查。
3. 使用临时 keychain 导入 `APPLE_CERTIFICATE_BASE64`，只接受证书身份前缀为 `Developer ID Application:` 且 Team ID 匹配的 identity。
4. 由内向外签名，包含安全时间戳和 `--options runtime`；拒绝 ad hoc signing；用 `codesign --verify --deep --strict` 验证最终 app。
5. 将签名 app 压缩为公证输入，调用 `xcrun notarytool submit --wait`，再 `xcrun stapler staple/validate`，最后生成发布 zip。
6. 解压“最终发布 zip”再次执行 Universal、codesign、stapler 和 `spctl --assess --type execute` 检查，保证验证对象就是上传对象。
7. 提供不读取 Secrets 的 dry-run，供静态、集成、系统测试重复验证 workflow 逻辑。

## 6. 原子测试用例

### TC-REL-ARCH — 对应 AC-01

- **测试目的**：确认 Release 编译和最终 app 的所有 Mach-O 同时包含 `x86_64` 与 `arm64`。
- **前置条件**：workflow 和发布脚本可读；CI 有 Qt macOS SDK；若做 artifact 检查，已有解压后的 app 和 zip。
- **输入数据**：`CMAKE_OSX_ARCHITECTURES="x86_64;arm64"`、`lipo -archs`、Universal 资产名。
- **操作步骤**：静态检查 workflow；运行发布脚本的架构检查；对最终 zip 解压后递归执行 `lipo -archs`。
- **预期结果**：每个 Mach-O 都含两种架构，资产名称为 `macOS-universal.zip`。
- **后置条件**：删除仅用于验证的临时解压目录，不修改 app 内容。
- **测试代码**：[`tests/quality_release.py`](../tests/quality_release.py) R-01、[`tests/quality_release_system.py`](../tests/quality_release_system.py) `TC-REL-SYSTEM-UNIVERSAL`。

### TC-REL-DEPS — 对应 AC-02

- **测试目的**：防止发布 zip 仅包含构建生成的 thin app 而没有 Qt 运行时。
- **前置条件**：`macdeployqt` 可执行；app 已构建。
- **输入数据**：`QT_ROOT_DIR/bin/macdeployqt`、app bundle 和其 `Contents`。
- **操作步骤**：运行 `macdeployqt APP -always-overwrite`；检查 workflow/script 中不存在直接 zip 前跳过部署的路径；对最终 app 检查 `Contents/Frameworks` 或部署后的 Qt plugin。
- **预期结果**：Qt 依赖被复制到 app 内，最终 app 可脱离 CI Qt 安装运行。
- **后置条件**：后续签名必须在部署完成后进行；失败时停止发布。
- **测试代码**：`quality_release.py` R-02、静态 ST-19。

### TC-REL-SECRETS — 对应 AC-03

- **测试目的**：确认 workflow 使用已配置的五个 Secrets，且仓库没有硬编码值。
- **前置条件**：GitHub Secrets 名称可查询但值不可读取。
- **输入数据**：五个 Secret 名称和 release workflow 文本。
- **操作步骤**：执行 R-03；扫描仓库代码和报告，禁止出现证书 base64、App 专用密码或证书密码值。
- **预期结果**：五个 `secrets.NAME` 均显式传入脚本环境，输出和代码不包含值。
- **后置条件**：不改变 Secrets；不打印环境变量。
- **测试代码**：`quality_release.py` R-03/R-07。

### TC-REL-CERT — 对应 AC-04

- **测试目的**：确认导入的 p12 不是开发/自签名证书，并且属于指定 Team ID。
- **前置条件**：CI runner 上存在 `security`；Secret 提供 p12 base64 和密码。
- **输入数据**：`APPLE_CERTIFICATE_BASE64`、`APPLE_CERTIFICATE_PASSWORD`、`APPLE_TEAM_ID`。
- **操作步骤**：base64 解码到临时文件；导入临时 keychain；读取 `security find-identity -p codesigning`；匹配 `Developer ID Application:` 和 `(${APPLE_TEAM_ID})`。
- **预期结果**：身份匹配；否则脚本以非零退出，不生成发布 zip。
- **后置条件**：删除临时 p12 和 keychain；不把 identity 私钥写入仓库。
- **测试代码**：发布脚本证书导入段、`quality_release.py` R-04。

### TC-REL-SIGN — 对应 AC-05

- **测试目的**：确认签名包含 Hardened Runtime、安全时间戳且非 ad hoc。
- **前置条件**：Developer ID identity 已导入；Qt 依赖已经部署。
- **输入数据**：app 内 Mach-O、framework、plugin 和外层 app。
- **操作步骤**：由内向外调用 `codesign --force --timestamp --options runtime`；执行 `codesign --verify --deep --strict`；读取 `codesign --display --verbose=4`。
- **预期结果**：包含 `Authority=Developer ID Application`、`Timestamp=`、`runtime`；不包含 ad hoc/no Team ID。
- **后置条件**：签名后禁止再修改 app 内容；任何修改必须重新签名和公证。
- **测试代码**：发布脚本签名段、`quality_release.py` R-04。

### TC-REL-NOTARIZE — 对应 AC-06

- **测试目的**：确认 Apple 公证流程完成且 ticket 写回 app。
- **前置条件**：签名验证通过；CI Secrets 可用；runner 可访问 Apple notary service。
- **输入数据**：签名 app 的临时 zip、Apple ID、App 专用密码、Team ID。
- **操作步骤**：执行 `xcrun notarytool submit --wait`；执行 `xcrun stapler staple APP`；执行 `xcrun stapler validate APP`。
- **预期结果**：notarytool 返回成功；stapler staple/validate 返回 0。
- **后置条件**：只保留最终 stapled app 和 release zip；删除临时公证 zip。
- **测试代码**：发布脚本公证段、`quality_release.py` R-05。

### TC-REL-ARTIFACT — 对应 AC-07

- **测试目的**：验证用户下载并解压的确切 zip，而非未压缩的中间 app。
- **前置条件**：已生成最终 `Fovelle-*-macOS-universal.zip`。
- **输入数据**：最终 zip。
- **操作步骤**：`ditto -x -k ZIP TEMP`；递归 `lipo -archs`；运行 `codesign --verify`、`stapler validate` 和 `spctl --assess --type execute --ignore-cache`。
- **预期结果**：所有命令返回 0，Gatekeeper 接受 app。
- **后置条件**：删除临时解压目录；GitHub Release 只上传已验证 zip。
- **测试代码**：发布脚本最终验证段、`quality_release_system.py` artifact 分支。

### TC-REL-SAFETY — 对应 AC-08

- **测试目的**：验证 dry-run 可重复、不会消耗 Secret 或发起 Apple 网络操作，且错误有明确非零退出。
- **前置条件**：不设置五个 Apple Secrets；bash 可执行。
- **输入数据**：`RELEASE_DRY_RUN=true`、fixture 路径。
- **操作步骤**：执行 `bash dist/scripts/package-macos-release.sh`；检查退出码、输出关键词和运行时间；扫描脚本禁止 `set -x`/secret echo。
- **预期结果**：返回 0，≤5 秒，输出流程摘要但不输出凭据；正式模式缺少必需环境变量时返回非零。
- **后置条件**：不生成 app、zip、keychain 或 Apple submission。
- **测试代码**：`quality_release.py` R-07/R-08、`quality_release_system.py` `TC-REL-SYSTEM-DRYRUN`。

### TC-REL-GATES — 对应 AC-09

- **测试目的**：确认静态、单元、集成和系统测试均产生可审计 JSON。
- **前置条件**：构建目录已存在；质量脚本可执行。
- **输入数据**：当前工作树、测试二进制、发布脚本。
- **操作步骤**：按静态→单元→集成→系统顺序执行所有 runner；读取 `reports/evidence/*.json`。
- **预期结果**：静态 ST-01～ST-19、单元 48 项、集成 I-01～I-16、系统用例均通过；每条记录包含实际值与期望值。
- **后置条件**：保留 JSON 证据，测试不修改用户设置或发布远端资产。
- **测试代码**：[`tests/quality_static.py`](../tests/quality_static.py)、[`tests/quality_unit_runner.py`](../tests/quality_unit_runner.py)、[`tests/quality_integration.py`](../tests/quality_integration.py)、[`tests/quality_release_system.py`](../tests/quality_release_system.py)。

### TC-REL-TIMING — 对应 AC-10

- **测试目的**：确认发布 orchestration 和应用系统负载满足时间/资源质量要求。
- **前置条件**：Cocoa 测试二进制存在；桌面测试串行执行。
- **输入数据**：dry-run、全屏合成事件、3 次 app 启动/每次保持 0.8 秒。
- **操作步骤**：记录平均、P99、最大响应时间、吞吐量、CPU、RSS、句柄和 socket；与阈值比较。
- **预期结果**：所有 performance flags 和 S-01～S-14 为 true；dry-run ≤5 秒。
- **后置条件**：关闭测试进程，保留性能 JSON；主机 I/O 标记为环境观察值。
- **测试代码**：`quality_release_system.py`、[`tests/quality_fullscreen_system.py`](../tests/quality_fullscreen_system.py)、[`tests/quality_system_probe.py`](../tests/quality_system_probe.py)。

## 7. 执行顺序

1. 静态：`quality_static.py`，包含 ST-19 和所有 Python/bash 契约。
2. 单元：`quality_unit_runner.py`，完整 Qt 测试。
3. 集成：`quality_integration.py`，包含 I-16 Release dry-run contract。
4. 系统：`quality_release_system.py`、Cocoa 功能/标题栏/全屏/资源探针；若 CI 提供真实 Release artifact，再启用 artifact 分支。

真实 Apple 公证是外部服务副作用，只在 tag Release workflow 中执行；本地测试不得用真实凭据替代 dry-run。
