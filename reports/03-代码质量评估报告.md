## 1. 结论摘要

本次改造的精益性和功能性达到验收目标：品牌身份集中更新为 Fovelle，版本从 `0.1.0` 开始，Bundle ID 为 `io.github.inostarlin-passion.Fovelle`，CI/CMake/deploy 链路收敛到 macOS，Windows/Linux 支持资产已按要求删除。现有文件名、类名、函数名和变量名未做品牌重命名；保留的 `qview_*.ts` 和 `qView*.icns` 仅是结构/资源文件名，不是运行时身份。

在本机 macOS arm64 启动烟囱负载上，30 次样本平均 0.125 s、P99/最大 0.160 s、吞吐 7.98 次/s，峰值 RSS 43.53 MiB，swap 和块 I/O 均为 0。QtTest 的 6 个断言、CTest 的 1 个测试、CMake updater 开关开/关两条构建路径均通过。

以下项目仍是边界而非失败：真实 Fovelle GitHub API 响应、Apple codesign/notarization、Qt 5.15 实机矩阵、长时间图片浏览的 P99、网络 I/O、稳定句柄计数、clang-format workflow 和正式发布机资源阈值。

## 3. 设计与实现质量

### 3.1 身份边界清晰

- `src/main.cpp` 设置组织名、组织域、应用名和完整版本字符串；这与 Qt 对 QSettings、命令行和版本属性的定义一致，参考：[Qt QCoreApplication](https://doc.qt.io/qt-6/qcoreapplication.html)。
- `CMakeLists.txt` 同时设置目标名称、`MACOSX_BUNDLE`、自定义 `Info.plist`、GUI identifier 和 Bundle 版本；这符合 CMake 对 macOS Application Bundle 的模型，参考：[CMake Bundle plist](https://cmake.org/cmake/help/latest/prop_tgt/MACOSX_BUNDLE_INFO_PLIST.html)。
- `dist/mac/Info.plist.in` 直接声明 `CFBundleIdentifier`、名称和版本，避免只依赖开发机默认值；Apple 将 Bundle ID 定义为应用的唯一标识，参考：[Apple Bundle ID](https://developer.apple.com/documentation/bundleresources/information-property-list/cfbundleidentifier)。
- About 中保留 qView 的历史来源和版权语境，同时单列 Fovelle 2026 modifications，避免把衍生项目误写成上游原项目。

### 3.2 平台收敛完整

- CMake 在非 Apple 配置时明确失败，并移除 X11、Win32、Linux 安装和平台源文件选择。
- `qvwin32functions.*`、`qvlinuxx11functions.*`、`dist/win`、`dist/linux` 以及对应部署脚本已删除。
- `build.yml` 只保留 macOS 矩阵，`test.yml` 的单元、clang-tidy、format job 全部为 macOS；nightly 分支由 `master` 改为 `main`。
- `macdeploy.sh` 使用 `Fovelle.app` 和 CMakeCache 版本，修复了原脚本把 `$0` 当作版本参数以及读取不存在 `qView.pro` 的问题。

### 3.3 updater 与可维护性

- API 和下载页已切换到 `inostarlin-passion/Fovelle`；GitHub Releases 文档说明该 API 使用 repository releases 路径并返回 `tag_name`，参考：[GitHub REST releases](https://docs.github.com/en/rest/releases/releases?apiVersion=latest)。
- 解析器接受可选 `v` 前缀，并用 `QVersionNumber` 解析 `0.1.0`；这避免直接对带 patch 的 tag 调用 `QString::toDouble()` 得到 0。
- 版本比较接口仍沿用旧项目的 `double` 兼容边界，因此当前 `0.1.0` 能正确工作，但未来若 minor 版本超过 9，`major + minor / 10.0` 的表示法不适合作为完整 semver 排序。这是低优先级后续改进项，不影响本次首发版本验收。

### 3.4 测试设计质量

- 测试直接观察 Qt 对象属性和 QLabel 文本，没有修改生产代码以暴露测试专用状态。
- About 测试使用精确字符串比较，能捕获 copyright、换行、许可证、GitHub URL 和官网残留。
- 关闭在线检查和固定 `QT_QPA_PLATFORM=cocoa` 后，测试不依赖网络且避免 offscreen 与 Cocoa 原生实现不兼容。
- CMake updater 开关开/关都编译，降低“测试配置把生产代码排除”的风险。

## 4. 事实、推断与不确定性审计

### 4.1 事实

1. 本地 `origin` 是 `https://github.com/inostarlin-passion/Fovelle`，当前分支是 `main`。
2. CMakeCache 为 `CMAKE_PROJECT_NAME=Fovelle`、`CMAKE_PROJECT_VERSION=0.1.0`。
3. Bundle 的 `CFBundleIdentifier`、Bundle 名、可执行文件和两个版本字段均已实测。
4. QtTest、CTest、offline build、online-source build、YAML/XML/shell 检查均有成功输出。
5. qView 上游仓库和 GPLv3/Qt/CMake/Apple/GitHub API 依据均有公开链接记录。

### 4.2 推断

1. 根据本地 remote 和用户给出的 GitHub 地址要求，把 Fovelle GitHub 地址作为项目主链接；这不等于已经有可下载的 Fovelle Release。
2. 根据用户明确“暂无官网”，README/About 不放网站链接；这不构成互联网范围内的永久不存在证明。
3. 以启动烟囱门槛作为本次非功能验收的代理指标；它不能代表所有图片浏览工作负载。

### 4.3 不确定性

1. GitHub API 的 live response、限流、非 2xx、空 `tag_name` 和发布资产尚未在隔离网络测试中模拟。
2. PowerShell Homebrew runtime 在本机对最小命令均未及时返回，因此 PowerShell AST 语法没有本地正面证据；工作流 YAML 和 Bash 已验证。
3. 直接 Debug CMake 没有显式设置部署目标时，`LSMinimumSystemVersion` 为空；CI 的 `build.ps1` 会按 Qt 配置设置 `MACOSX_DEPLOYMENT_TARGET`，但未在本机 CI runner 上重放。
4. 本机 workflow 期望的 `clang-format` 不在直接 PATH；`xcrun clang-format` 对 `mainwindow.cpp` 的 CRLF/基线格式差异仍有提示，因此格式 job 需在 CI runner 上复核。
5. 句柄数、网络 I/O、持续存储 I/O 和正式 CPU 利用率上限没有需求数值，不能通过一次短采样补造。

## 5. 风险清单与后续建议

| 优先级 | 风险/改进项 | 建议 |
|---|---|---|
| P1 | 发布前没有真实签名/notarization 证据。 | 在 macOS CI 的 release workflow 中使用真实证书执行 `macdeploy.sh`，校验 `codesign --verify`、DMG 和 `xcrun notarytool` 输出。 |
| P1 | updater 只有编译和静态 URL 验证。 | 使用可控 HTTP fixture 覆盖 `v0.1.0`、无 v 前缀、非法 JSON、超时、非 2xx 和无 tag；不要让单元测试直接依赖 GitHub。 |
| P2 | 版本比较仍以旧 double 接口承载 semver。 | 后续将 `latestVersionNum` 和比较逻辑迁移到 `QVersionNumber` 或明确的 semver 值对象，覆盖 minor≥10 和 patch 比较。 |
| P2 | Qt 6.11 弃用警告。 | 逐步替换 `stateChanged`、`qAsConst`、旧 `QDateTime` 和已弃用 `NSWorkspace` API；将 warning policy 纳入 CI。 |
| P2 | 性能/资源阈值只覆盖启动烟囱。 | 明确图片尺寸、格式、窗口数、会话时长、CPU/RSS/句柄/网络 I/O 阈值，增加可重复的图片加载和长会话压力测试。 |
| P3 | 现有文件名保留旧 qView 片段，可能造成新贡献者误解。 | 遵守本次“不改文件名”约束；在项目迁移完成且有独立决策后，再单独规划资源/翻译文件迁移。 |

## 6. 最终质量判定

在已定义的本地验收范围内，Fovelle 改造达到“可构建、可运行、身份一致、macOS-only、可重复测试”的质量门槛；精益完整性、功能正确性、启动时间、烟囱资源和可测试性均有证据支持。对真实网络、Apple 发布服务和未定义的通用负载指标，报告保持条件结论，待后续发布环境补证后再升级为全面通过。
