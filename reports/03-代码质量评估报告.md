## 1. 事实、推断与不确定性

### 事实

- 源码中新增 `smallimageoneone`、Image 页勾选框和 `QVGraphicsView::shouldDisplaySmallImageAtOneToOne`。
- 打开和浏览都经过 `QVGraphicsView::postLoad()` 的统一缩放重算路径。
- Open With worker 在窗口析构前停止定时器并等待完成，worker 路径按值捕获。
- `.github/workflows/release.yml` 使用 `push.tags: v*`、`contents: write`、`GITHUB_TOKEN` 和 `softprops/action-gh-release@v3`。
- 静态、单元、集成和 Cocoa 系统证据均为通过。

### 推断

- 本地 Fovelle 的 Open With 异步路径与上游 [Issue #864](https://github.com/jurplel/qView/issues/864) 描述的生命周期风险是对应实现，因此按同一类根因修复；这不是声称两个仓库的提交历史相同。
- `OriginalSize` 不需要额外覆盖；对 `ZoomToFit` 和 `FillWindow` 的自动模式进行小图保护，符合“勾选后小图片按 1:1”的字面要求；手动缩放（无 calculated mode）不被设置强行改写。
- 默认关闭是最小兼容性选择：用户未勾选时保留既有自动缩放行为。

### 不确定性

- 尚未在 GitHub hosted runner 上实际推送 tag 并创建云端 Release；工作流的真实 runner、Qt 下载缓存、权限策略和 macOS 签名/公证仍需首次发布时验证。
- 资源探针的磁盘/网络值是主机级观测，可能包含背景活动；不能将全部 I/O 归因于 Fovelle。
- 1:1 的核心断言基于 zoom level、确定性图片尺寸和 viewport 逻辑，未做屏幕截图/OCR；Cocoa 渲染器的最终像素边界保留少量平台不确定性。

## 3. 功能正确性与不变量

### 3.1 图片显示策略

实现位于 [`src/qvgraphicsview.cpp`](../src/qvgraphicsview.cpp)：

1. `imageSize` 使用当前图片的有效原始显示尺寸。
2. `usableViewportSize` 使用 `getUsableViewportRect()`，不带 fit overscan。
3. 只有 `settingEnabled && windowResizeMode == Never && imageWidth < viewportWidth && imageHeight < viewportHeight` 才命中。
4. 自动 `ZoomToFit`/`FillWindow` 命中后目标比例为 `1.0`；`OriginalSize` 本身不需变换。
5. `calculatedZoomMode` 为空时不覆盖手动缩放，保持手动缩放不变量。
6. `settingsUpdated()` 更新成员后调用已有 `fitOrConstrainImage()`，所以用户在设置中改变选项时已加载图片也会重新计算。

### 3.2 打开/浏览一致性

图片加载完成后的 `postLoad()` 对首次打开和文件导航均执行同一套 fit/constrain 逻辑。测试先打开 `32×24` 图片，再切换到 `48×36` 图片，均验证 zoom level=1.0，并额外切换 `FillWindow` 验证小图保护仍成立。

### 3.3 Issue #864 生命周期

[`src/mainwindow.cpp`](../src/mainwindow.cpp) 的生命周期约束形成以下不变量：

- `isClosing` 后不启动新 worker；
- 同一窗口最多一个 Open With worker；
- future 使用 `filePath` 值捕获，不引用可变窗口状态；
- 完成结果必须匹配当前文件路径，否则丢弃；
- 窗口析构先停止 timer，再等待当前 future；
- 后续刷新通过 pending 标志排队，避免并发 `setFuture` 覆盖状态。

该设计直接针对 Qt 官方所述“QtConcurrent::run 不能取消”和“QFutureWatcher 可等待完成”的生命周期约束：[QFuture](https://doc.qt.io/QT-6/qfuture.html)、[QFutureWatcher](https://doc.qt.io/QT-6/qfuturewatcher.html)。

## 4. 时间行为与资源利用评估

最终系统探针工作负载为 4 类图片、每类 3 次独立启动、单次约 0.8 秒。当前证据的代表性指标如下：

| 指标 | 实测 | 门槛 | 结论 |
|---|---:|---:|---|
| 启动平均 | 5.98ms | 2.0s | 通过 |
| 启动 P99 | 7.39ms | 3.0s | 通过 |
| 启动最大 | 7.39ms | 5.0s | 通过 |
| 吞吐量 | 1.07 次/s | 0.5 次/s | 通过 |
| CPU 峰值（12 核归一化） | 5.72% | 100% | 通过 |
| RSS 峰值 | 726288 KiB | 786432 KiB | 通过 |
| 磁盘 I/O 峰值 | 4.11 MB/s | 500 MB/s | 通过 |
| 网络观测吞吐量 | 7.593 MiB/s | 64 MiB/s | 通过 |
| 网络字节增量（辅助观测） | 85.19 MiB | 不作进程归因门禁 | 记录 |
| 句柄 / socket 峰值 | 142 / 0 | 512 / 4 | 通过 |

这些数字证明本次测量窗口满足门槛，不代表所有机器和所有图片工作负载的长期 SLO。资源采样限制已写入 `system.json` 的 `limitations`。

## 6. Release 工作流质量

[`release.yml`](../.github/workflows/release.yml) 的职责边界清晰：tag 触发、checkout、Qt 安装、配置、构建、CTest、打包、创建 Release。`contents: write` 是 action 创建 Release 所需的最小仓库内容写权限；token 只通过 GitHub Actions secret 环境变量传入，不写入源代码。

当前使用 `@v3` 版本标签，符合 action 官方当前示例；如后续供应链策略要求更强可复现性，可将 action 改为提交 SHA 固定，但这不是本需求的必要设计扩展。

## 7. 总结

本次实现以最少新增状态完成了 Settings → Image 小图策略，并覆盖打开与浏览；以显式生命周期边界修复了 Issue #864 同类竞态；以单 workflow 实现 `v*` Tag 自动构建、测试、打包和 Release。静态、单元、集成、系统以及时间/资源门禁全部通过，代码质量要求评估为“通过”；剩余风险仅限于真实 GitHub runner 发布和平台像素渲染的外部验证。
