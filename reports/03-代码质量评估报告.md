# Fovelle macOS Release 代码质量评估报告

## 1. 评估范围与结论

评估对象：Universal 构建参数、Qt app 部署、Developer ID Application 签名、Hardened Runtime、Apple notarization/staple、Gatekeeper 验证、GitHub Secrets wiring，以及相应的静态/单元/集成/系统测试代码。

结论：实现满足本地可验证的精益完整性、功能正确性、时间行为和可测试性要求。真实 Apple 公证和最终 GitHub Release artifact 尚未在本地消费凭据验证，已明确标记为远端待确认，不将 dry-run 结果冒充为公证成功。

## 2. 根因证据链

历史 [Release run 32113103430](https://github.com/inostarlin-passion/Fovelle/actions/runs/32113103430) 在 `macos-14-arm64` 上成功，但只做了构建、测试和直接 `ditto`。下载并检查 [v0.1.0 Release zip](https://github.com/inostarlin-passion/Fovelle/releases/download/v0.1.0/Fovelle-v0.1.0-macOS.zip) 得到：

| 质量属性 | 旧资产实测 | 评价 |
|---|---|---|
| 架构 | thin `arm64` | 无法直接运行于 Intel |
| 签名 | `adhoc,linker-signed` | 不是 Developer ID Application |
| Team ID/时间戳 | 未设置/无安全时间戳 | 不具备外部分发信任链 |
| Qt 依赖 | `@rpath/Qt*.framework`，app 内无 frameworks | 不是 self-contained app |
| Gatekeeper | spctl 拒绝，报告资源签名异常 | 与“App 已损坏”现象一致 |

事实与推断分开：旧资产的命令输出是事实；“用户看到的具体弹窗一定只由 ad hoc 签名触发”是推断。实现同时修复架构、依赖部署和信任链，避免只针对弹窗文案做单点修补。

## 3. 四项代码质量要求

### 3.1 精益完整性：通过

- Universal 只在 Release workflow 开启，不改变普通本地开发构建，避免增加开发反馈成本。
- 发布逻辑集中在一个可审计脚本 [`dist/scripts/package-macos-release.sh`](../dist/scripts/package-macos-release.sh)，workflow 只负责传入构建参数和 Secret 名称。
- 复用 macdeployqt、系统 `security/codesign/xcrun/spctl/lipo/ditto`，没有引入第三方签名 action 或新的凭据格式。
- 证书导入使用临时 keychain，退出时清理；最终 zip 是签名、公证、staple 完成后的副本。
- 不使用 `codesign --sign -`；验证阶段才使用 `--deep`，签名阶段按嵌套代码由内向外处理。

静态 ST-01～ST-19 全部通过，Release 专项 R-01～R-08 全部通过，证据见 [`static.json`](evidence/static.json) 和 [`release.json`](evidence/release.json)。

### 3.2 功能正确性：通过（远端公证待确认）

| 不变量 | 实现 | 检查 |
|---|---|---|
| 每个 Mach-O 同时含 arm64/x86_64 | `assert_universal_app` + `lipo -archs` | R-01、ST-19、artifact system branch |
| app 自包含 Qt 依赖 | `macdeployqt -always-overwrite` 在签名前执行 | R-02 |
| 证书身份可信且归属指定 Team | `security find-identity` 前缀和 Team ID 双校验 | R-04 |
| 外部分发签名有效 | timestamp + Hardened Runtime + `codesign --verify` | R-04、R-06 |
| 公证票据存在 | `notarytool --wait` + `stapler staple/validate` | R-05、R-06 |
| 用户下载对象可接受 | 最终 zip 解压后再 spctl | R-06 |
| Secret 不进入仓库/日志 | workflow 只引用名称；脚本无 trace/secret echo | R-03、R-07 |

Apple 官方说明 Developer ID 分发需要正确的 distribution certificate、Hardened Runtime 和安全时间戳，参见 [Creating distribution-signed code](https://developer.apple.com/documentation/xcode/creating-distribution-signed-code-for-the-mac/)；notarytool/stapler 流程参见 [Customizing the notarization workflow](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow)。

### 3.3 时间行为：通过本地阈值

| 负载 | 平均 | P99 | 最大 | 吞吐量 | 结论 |
|---|---:|---:|---:|---:|---|
| 全屏状态确认 | 14.0 ms | 28.0 ms | 28.0 ms | 71.43/s | 通过 |
| app 启动探针（3 次） | 0.005734 s | 0.008241 s | 0.008241 s | 1.1686/s | 通过 |
| Release dry-run | 由 `release-system.json` 固化，≤5 s 阈值 | — | — | — | 通过 |

资源探针同时验证 CPU、RSS、句柄、socket 和磁盘空间；主机 I/O/网络为环境观察值。完整数据见 [`system-fullscreen.json`](evidence/system-fullscreen.json)、[`system.json`](evidence/system.json) 和 [`release-system.json`](evidence/release-system.json)。Apple notarization 的等待时间受外部服务影响，不能被本地应用 P99 指标替代；正式 workflow 使用 `--wait`，确保未完成公证时不上传资产。

### 3.4 可测试性：通过

- **系统化生成**：AC-01～AC-10 一一映射到 TC-REL-ARCH～TC-REL-TIMING。
- **确定性控制**：脚本 dry-run 不读取 Secret；架构检查、签名检查、zip 解压检查均使用固定命令和明确退出码。
- **非侵入式观测**：使用 `lipo`、`codesign`、`stapler`、`spctl` 和 JSON 记录，不在生产 app 中加入测试开关。
- **外部输出可重放**：质量脚本输出 `pass`、`actual`、`expected`、返回码和 limitation；artifact 分支接收具体 app/zip 路径。
- **失败安全**：缺少 Secret、非 Developer ID identity、thin Mach-O、签名失败、公证失败、stapler/spctl 失败都会中止发布。
- **字段完整**：每个测试用例都显式包含“测试目的、前置条件、输入数据、操作步骤、预期结果、后置条件”六个字段，定义见 [`01-测试规格说明书.md`](01-测试规格说明书.md)。

## 5. 风险与边界

| 风险 | 控制措施 | 当前状态 |
|---|---|---|
| Qt SDK 不是 Universal | workflow 显式要求两架构，脚本对每个 Mach-O 执行 lipo，失败即停止 | 远端待执行 |
| 证书不是 Developer ID Application | identity 前缀和 Team ID 校验 | 远端待执行 |
| notarization 服务失败/超时 | `notarytool --wait` 非零即停止，不上传旧/未公证 zip | 已实现 |
| 资产在上传前被修改 | 对最终 zip 解压后重新验证 | 已实现 |
| Secret 泄露 | 临时 keychain、无 `set -x`、无 secret echo；GitHub Secrets 只引用名称 | 已实现；本会话曾发生诊断输出泄露，建议轮换 |
| 本地环境差异 | 本地 Homebrew Qt 为 arm64-only，未伪造 Universal 成功；Qt 官方文档确认 Universal 配置方式 | 明确记录 |
| 外部服务不可观测 | JSON 保留 limitation，远端 run 需保存 notarytool 输出和 spctl 结果 | 待远端确认 |

## 6. 研究依据

- [Qt for macOS — Architectures](https://doc.qt.io/qt-6/macos.html)：Universal 的 CMake 配置方式。
- [CMake `OSX_ARCHITECTURES`](https://cmake.org/cmake/help/latest/prop_tgt/OSX_ARCHITECTURES.html)：target 架构属性来源。
- [Apple distribution signing](https://developer.apple.com/documentation/xcode/creating-distribution-signed-code-for-the-mac/)：Developer ID、timestamp、Hardened Runtime 和签名顺序。
- [Apple notarization](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution?changes=_5)：外部分发的 notarization/ticket 要求。
- [Apple common notarization issues](https://developer.apple.com/documentation/security/resolving-common-notarization-issues)：Developer ID、timestamp、spctl 验证。
- [GitHub Actions Secrets](https://docs.github.com/en/actions/concepts/security/secrets)：Secrets 只通过 workflow 显式注入。

## 7. 最终评价

本次修复把 Release 从“构建目录直接压缩”提升为可验证的 macOS distribution pipeline：Universal → dependency deployment → Developer ID signing → notarization → staple → final zip verification。代码和本地门禁达到交付标准；最终发布是否被 Apple/Gatekeeper 接受，必须以修复提交在 GitHub runner 上完成真实公证并验证上传 zip 的结果为准。
