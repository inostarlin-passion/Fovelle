## 2. 最新 GitHub Actions 失败根因

最新 [Release run 32124573280](https://github.com/inostarlin-passion/Fovelle/actions/runs/32124573280) 的 job `95672173903` 已被取消；其日志给出以下顺序：

```text
Universal architecture verified for 26 Mach-O files
Using signing identity: Developer ID Application: ...
build/Fovelle.app: valid on disk
Submission ID received
  id: 64a13a6f-ecaf-4c20-aa08-6c411b725f01
Successfully uploaded file
Waiting for processing to complete.
Current status: In Progress
...
##[error]The operation was canceled.
Terminate orphan process: pid (...) (notarytool)
```

事实是：签名步骤已通过 26 个 Mach-O 的签名、外层 app 验证和 Apple 上传；阻塞发生在 Apple submission 已创建后的服务端处理阶段。`notarytool --wait` 每隔约 5～20 秒输出 `Current status: In Progress`，从 `10:03:34Z` 持续到 `11:26:11Z`。这排除了本地 `codesign` 死锁。用户取消后，GitHub 清理阶段终止了遗留 `notarytool` 进程；`stapler`、Gatekeeper、最终 zip 和 GitHub Release 上传均未执行。

推断是：原脚本只使用 `--wait`，没有 `--timeout`；Apple 服务异常缓慢时，脚本会把等待一直保持到用户取消或 GitHub 默认 job 上限。`notarytool` 的进度输出证明它仍在轮询，而不是 shell 无输出挂死。Apple submission 在取消时的最终状态未知，不能把它解释为 Accepted 或 Invalid。

修复方式是：保留已有私钥 ACL/keychain 修复；新增默认 `NOTARIZATION_TIMEOUT=30m` 和格式校验，调用 `notarytool submit --wait --timeout "$NOTARIZATION_TIMEOUT" --verbose`；非零返回或超时立即 fail-closed，不执行 stapler、Gatekeeper 或上传；workflow 为签名步骤设置 45 分钟、job 设置 60 分钟。日志仍保留 submission ID，便于后续用 `notarytool info/log` 查询。

## 2. 历史 Release 根因证据

### 2.1 workflow 成功不代表产物可信

历史 [Release run 32113103430](https://github.com/inostarlin-passion/Fovelle/actions/runs/32113103430) 的 job 成功，但日志中的关键步骤只有：

```text
Image: macos-14-arm64
Run cmake -S . -B build -DBUILD_TESTS=ON ...
Run ditto -c -k --sequesterRsrc --keepParent build/Fovelle.app ...zip
```

没有 Universal 架构参数，也没有 `macdeployqt`、`codesign`、`notarytool`、`stapler` 或 `spctl` 步骤。GitHub Actions 只验证了“命令成功生成并上传 zip”，没有验证用户可信任的 macOS distribution artifact。

### 2.2 已下载并检查旧资产

旧资产 [Fovelle-v0.1.0-macOS.zip](https://github.com/inostarlin-passion/Fovelle/releases/download/v0.1.0/Fovelle-v0.1.0-macOS.zip) 的本地审计结果：

| 检查 | 结果 |
|---|---|
| zip 大小 | 约 3.7 MiB |
| 解压 app 大小 | 约 6.0 MiB |
| 主二进制 | `Mach-O 64-bit executable arm64` |
| `lipo -info` | thin `arm64` |
| CodeDirectory | `adhoc,linker-signed` |
| Developer ID Authority | 不存在 |
| TeamIdentifier | `not set` |
| Qt framework | `Contents/Frameworks` 不存在；主程序依赖 `@rpath/Qt*.framework` |
| Gatekeeper | `code has no resources but signature indicates they must be present` |

因此根因是三个独立缺口叠加：单架构、自包含部署缺失、正式签名/公证缺失。Apple 文档明确要求外部分发使用 Developer ID、Hardened Runtime、时间戳并完成 notarization；详见 [分发签名](https://developer.apple.com/documentation/xcode/creating-distribution-signed-code-for-the-mac/)、[公证](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution?changes=_5)。

## 3. 实施修复

### 3.1 Universal

[`.github/workflows/release.yml`](../.github/workflows/release.yml) 的 Configure 步骤增加：

```text
-DCMAKE_OSX_ARCHITECTURES="x86_64;arm64"
```

该顺序与 Qt 官方 Universal 示例一致。发布资产名改为 `Fovelle-<tag>-macOS-universal.zip`。

### 3.2 Qt 运行时部署和产物验证

新增 [`dist/scripts/package-macos-release.sh`](../dist/scripts/package-macos-release.sh)：

- 使用 `QT_ROOT_DIR/bin/macdeployqt` 部署 Qt framework/plugin。
- 对 app 内所有 Mach-O 执行 `lipo -archs`，拒绝 thin 文件。
- 对最终 zip 解压后的 app 再重复检查，保证检查对象就是上传对象。

### 3.3 Developer ID 签名和 Apple 公证

脚本使用临时 keychain 导入 `APPLE_CERTIFICATE_BASE64`，通过 `security find-identity` 只接受 `Developer ID Application:` 且 Team ID 匹配的身份，并确认存在可签名私钥；随后：

1. 使用 `security import -A -t cert -f pkcs12 -T /usr/bin/codesign` 给私钥配置非交互式签名 ACL；执行 `security list-keychain -d user -s`，使一次性 keychain 可被用户安全上下文搜索；该导入形式与 [GitHub macOS runner 证书安装文档](https://docs.github.com/en/actions/how-tos/deploy/deploy-to-third-party-platforms/sign-xcode-applications)的 p12 示例一致。
2. 由内向外签名，包含 `--timestamp` 和 `--options runtime`。
3. `security find-key -s -t private` 确认 PKCS#12 确实带有私钥；identity-scoped partition 更新失败时记录 warning 并继续。
4. `codesign --verify --deep --strict` 验证签名、Authority、Hardened Runtime 和时间戳。
5. 验证 `NOTARIZATION_TIMEOUT` 为正整数秒/分/小时格式，默认 `30m`；使用 `xcrun notarytool submit --wait --timeout "$NOTARIZATION_TIMEOUT" --verbose` 提交公证。超时或非零返回立即停止，不执行后续发布步骤，并保留 submission ID 供 `notarytool info/log` 查询。
6. `xcrun stapler staple/validate` 写入并验证 ticket。
7. `spctl --assess --type execute --ignore-cache` 验证 Gatekeeper。
8. 生成 zip 后解压，重复 `codesign`、`stapler`、`spctl` 验证。

GitHub workflow 显式传入五个已配置 Secret 名称，仓库没有写入 Secret 值。GitHub 官方说明 Secret 必须显式作为 workflow 环境变量或 input 使用，见 [GitHub Actions Secrets](https://docs.github.com/en/actions/concepts/security/secrets)。
