# macOS 设置窗口统一重构

## 问题、依据与边界

旧设置窗按每个面板的自然内容计算宽度，切换时横向移动。General 的选项分散，Mouse 的分组内边距偏大，Shortcuts 使用未分类的交替色表格，编辑操作主要依赖双击。

- **依据**。Apple HIG 将顶置工具栏切换独立设置面板视为 macOS 的典型模式，设置窗口可随当前面板调整高度。Apple 的 Form 文档以对齐的垂直布局描述 macOS 表单。 [Apple HIG](https://developer.apple.com/design/human-interface-guidelines/settings) · [Apple Form 文档](https://developer.apple.com/documentation/swiftui/form)
- **依据**。Fovelle 使用 Qt Widgets 控件，顶部导航由 AppKit 的 `NSToolbar` 和 SF Symbols 绘制。CMake 与 qmake 的 macOS 部署目标均为 15.0。设置值、快捷键和最后打开的面板已有持久化逻辑。
- **推断**。采用 512 pt 客户区、紧凑原生工具栏、相同页边距和简洁的分组标题，可以保留切换效率，并减少左右跳动和各页的空白差异。尺寸是对本应用文案、控件和现实屏幕空间的设计选择。
- **假设**。使用系统字体和项目提供的五种语言。屏幕可用高度不足时允许纵向滚动。
- **约束与未知**。复用现有 Qt/AppKit 架构、菜单入口和存储键。按屏幕可用高度限制窗口并保持内容可滚动。用当前主机验证实际呈现，最低支持版本的实际样式需要在 macOS 15 上复验。

## 实现与正确性

1. 保留三个横向原生面板，用紧凑工具栏承载 AppKit 分段控件，标签和 SF Symbols 同时可见。首轮截图确认紧凑工具栏会省略普通工具栏项的标签。Tab 索引只切换内容，512 pt 宽度在三个面板中相同。高度由当前面板在固定宽度下的布局计算，画面空间不足时由滚动区提供剩余内容。首次居中使用最终固定的客户区尺寸，加上 Cocoa 实测的窗口边距，使临时的原生内容尺寸不影响放置。 [Qt Cocoa 窗口轮廓计算](https://raw.githubusercontent.com/qt/qtbase/6.11/src/plugins/platforms/cocoa/qcocoawindow.mm)
2. General 的五组和 Mouse & Trackpad 的三组使用相同的左标签、右控件网格、组间分隔与行距。表单沿用原设定对象和信号，重新布局不改变设置项的数据流。文件关联是常规次要按钮。
3. Shortcuts 以分类标题组织双列表格。每个可编辑行保存对应动作在快捷键列表中的索引，分类标题没有该索引，因此编辑只作用于真正的动作。显示使用 Qt 的 macOS 快捷键符号。提交前检查冲突，冲突期间关闭保存入口，恢复默认将当前动作的默认值放入编辑器，确认后才保存。
4. 为固定宽度、多语言表单、快捷键行与真实动作的映射、冲突及恢复、原生外观和原有持久化分别运行回归，并以实际窗口截图复核分组、密度和浅深模式。

# 移除双图对比加载预算的技术设计

## 问题、假设与约束

| 类型 | 内容 |
| --- | --- |
| 依据 | `QVComparison::startPending` 按 A、旧 B 和屏幕绘制面积计算窗口余量。`QVImageLoader::readComparisonImage` 在完整解码前检查文件字节和像素估算，并与其他窗口共享原子预留。解码后还会比较保留估算与预留。预算取物理内存的一半和 16 GiB 的较小值。 |
| 依据 | SVG 使用逻辑尺寸和按需渲染，窗口中的实际位图开销可以远低于按逻辑像素估算的整幅栅格开销。现有比较加载器调用普通完整加载路径，再经独立比较队列和请求编号交付。 |
| 推断 | 去掉比较专用估算、预检和记账后，合法的静态图像能进入实际解码，窗口尺寸、A 或旧 B 的估算以及其他窗口持有的结果都无法否决该次请求。 |
| 假设 | “内存足够”对应实际解码和呈现所需的资源可分配。文件有效性、动画准入、格式或平台的表示与解码约束继续由现有逻辑处理。 |
| 约束 | 变更限于比较专用预算。复用现有静态图解码和渲染路径，维持普通打开、后台预加载以及共享解码器的既有策略。Qt 的进程级图像分配防护和格式专用约束属于共享解码层。 |
| 未知 | 系统、解码器和 GPU 的可用资源会变化。测试主机的成功只能证明对应样本在该次运行中可加载。进程被操作系统终止时没有应用级错误回调。 |

## 设计与正确性论证

1. **取消全部比较预算。** 将候选加载接口收敛为路径参数。移除窗口余量计算、文件字节和像素开销估算、原子预留与退还、解码后预算复核和预算错误文案。清理仅供比较预算使用的原生尺寸探测。普通图像信息窗口仍读取原文件字节字段。
2. **以实际解码结果为准。** 记录文件版本，沿用现有动画识别，并在完整读取前后检查版本及取消状态。可提交图像包括有效 Qt 栅格、矢量文档、原生 SDR 和原生 HDR。空结果或解码错误返回加载失败。任务捕获可恢复的 `std::bad_alloc` 并返回内存提示。复用同一个完整读取入口意味着 RAW、HDR、普通栅格和矢量图继续使用各自的正常呈现路径。
3. **保持提交原子性。** 独立比较队列继续串行执行候选解码。只有未取消、请求号仍有效且对比仍开启的结果能进入提交逻辑。失败分支在更换候选前返回，保留已显示的 B。`removeCandidate` 和 `leave` 仍取消任务并通过视图的所有权释放内容。
4. **证明。** 对可读、版本稳定、未取消且通过动画检查的文件，控制流进入 `readFile`。从接收路径到提交，决策仅依赖文件状态、解码结果与当前请求身份。因此，原窗口预算、共享预算及估算复核不会阻止加载。若解码返回有效结果且请求仍有效，提交使用该图像既有的尺寸与呈现方式。若读取失败、版本变化、请求失效或解码发生可捕获的分配失败，流程不会替换已提交图像。
5. **回溯核验。** 先追踪选择至提交的调用链，再反向检索物理内存查询、窗口记账、关联探测和翻译，最后用旧实现运行新增大图用例，确认它们能触发旧门槛。修改后用相同用例、双 16K HDR 和默认 CTest 验证。

# 最大化双 16K HDR 对比的技术设计

## 问题、前提与约束

在 macOS 最大化窗口中同时对比两张 16K HDR 静态图片。按 16384 × 9216 的 16∶9 上边界验收双图，覆盖 15360 × 8640 的 16K UHD。两张图保留原始分辨率及原生 HDR 图像。超预算候选应被拒绝，并保留当前画面。适用前提是系统 ImageIO／Core Image 可解码该格式，Metal 支持其源尺寸，且设备预算足以容纳两张图和画布。全分辨率 HDR 图像继续使用常规渲染链路的首帧及窗口失焦机制。

## 依据、推断与未知

| 类型 | 结论 |
| --- | --- |
| 依据 | 上一轮在 1728 × 984、DPR 2 的最大化比较窗口复现候选余量归零。参考图约 372.1 MiB，画布估算约 155.7 MiB，超过旧的 512 MiB 窗口预算。 [原问题实测](../build-thumbnail-release/test-results/comparison-hdr-budget/same-file-window.log) |
| 依据 | 完整解码路径保留原生 HDR 和 SDR 图像图，Qt 位图可随格式和系统消耗源尺寸分配。Metal 超过持久全图表面门槛时继续使用视口纹理，每个窗格的 Metal 图层最多三张 RGBA16Float drawable，准备阶段另用一张同格式纹理。 [加载器](../src/qvimageloader.cpp) · [原生渲染器](../src/qvcocoafunctions.mm) |
| 依据 | 独立 Core Image 与 ImageIO 探针生成了两个目标尺寸的 JPEG，并识别出 ISO HDR 增益图。Apple 给出了 Core Image 尺寸随设备变化的约束，以及现代 Mac Metal 设备支持的纹理尺寸。 [本机夹具探针](../build-thumbnail-release/test-results/comparison-16k-hdr/imageio-16k-probe.log) · [Core Image 尺寸限制](https://developer.apple.com/library/archive/documentation/GraphicsImaging/Conceptual/CoreImaging/ci_performance/ci_performance.html) · [Metal 设备限制](https://developer.apple.com/metal/Metal-Feature-Set-Tables.pdf) |
| 依据 | 使用预先生成的两个 16384 × 9216 文件独立运行最大化窗口，系统记录峰值内存足迹约 12.1 GiB。将大图估算提高到两张上边界夹具及画布约 13.7 GiB，保留实测余量。 [独立运行与资源测量](../build-thumbnail-release/test-results/comparison-16k-hdr/two-max-16k.log) |
| 推断 | 旧上限甚至无法容纳一张 16K 图的原加载估算。为完整路径建立随设备内存调整的预算并移除超额预览分支，可在容量允许时保留两张原生图的分辨率和动态范围。 |
| 未知 | 各相机格式、系统版本和外接显示器的解码器峰值不同。账面预算约束应用的准入和持有估算。系统可用内存、Core Image 缓存及非对比窗口占用变化会影响实际结果。 |

## 方案与正确性论证

1. 进程启动后依据 `hw.memsize` 计算预算，取物理内存一半与 16 GiB 的较小值。查询失败时沿用 512 MiB 保守预算。每窗口扣除 A 的保留成本、已有 B 的保留成本，以及当前显示器或实际组件中较大绘制区域的 32 B/物理像素估算，以涵盖当前屏幕内的最大化。
2. 每张图的估算包含文件字节加 8 MiB 固定开销。像素部分在解码阶段按 32 B/像素预留，交付后的保留估算按 24 B/像素核算。超过 64 Mi 像素的源进入更高档，解码预留为 56 B/像素，保留估算为 40 B/像素，为大型源图及其 GPU 工作区留出余量。预检取 Qt 与 ImageIO 报告的较大面积，保留量再核对结果源尺寸和实际 Qt 位图尺寸。编码量计入同一预算。图像乘法及固定项做饱和检查，窗口以饱和扣减避免下溢。
3. 同时满足窗口剩余容量和进程级候选图预留条件才开始完整解码。超额即返回现有预算错误，删除比较专用的缩略图替代路径及其状态。通过文件版本和异步请求编号确认结果仍然有效，再交付完整图像。旧 B 在新图发布前继续持有估算，失败只更新错误状态。
4. 记总预算为 C，A 和画布的核算为 A、D，已显示 B 的保留成本为 B，待加载候选的峰值估算为 P。窗口提交前必须满足 P ≤ max(0, C − A − D − B)。进程原子比较并预留 P，令候选图预留总量 U 满足 U + P ≤ C。解码后的保留量 R 只有在 R ≤ P 时才能交付，因此释放 P − R 不会突破任何已通过的账面条件。预留随结果、取消交付和已显示候选的生命周期释放。文件变更、取消和过期请求不能替换现有图。
5. 对 16384 × 9216 的 A 和 B，像素核算分别为 5.625 GiB 和 7.875 GiB。以 3456 × 2234 物理画布计，画布约 0.23 GiB，加固定项约 0.016 GiB 和两张文件字节。在具有 16 GiB 比较预算的设备上，两张文件合计小于约 2.25 GiB 时通过窗口预检。共享候选预留繁忙时仍以实际余量为准。现有原生路径为通过预检且可解码的 HDR 图保留源图，并从源图渲染各自视口。

# 双图对比以 HDR 为参考图时的加载预算

## 问题、前提与约束

用户先在窗口加载 HDR 参考图 A，再进入双图并选择 B。B 可能被预算预检拒绝，界面提示 “This image exceeds the comparison memory budget.”。本次覆盖 macOS 双图对比，包括首次选图、替换和退出。预算充足时优先走原生或现有完整解码路径。内存紧张时允许支持的静态图像以明确标示的 SDR 预览参与对比，沿用原始图像尺寸、方向和缩放坐标。原有单文件 64 MiB 编码上限和进程级 512 MiB 候选图分配上限继续约束解码。

## 检索与交叉核验

| 类型 | 发现 |
| --- | --- |
| 依据 | B 的拖放和选择文件入口都到达 `QVComparison::startPending()`。它从 512 MiB 中扣掉 A 的基准像素数乘 8、窗口绘制估算和已提交 B 的预留。窗口保留旧 B 直至新图成功。 [窗口接入](../src/qvcomparison.cpp) |
| 依据 | `readComparisonImage()` 最早用窗口余量检查编码大小，完整解码又需要最多一份 12 B/像素的图像估算加编码量及固定开销。既有 JPEG 预览仍须用同一窗口余量支付可能出现的全幅中间图。它解码完成后只保留预览预留。 [加载和预留](../src/qvimageloader.cpp) |
| 依据 | 随仓库提供的 ISO 增益图 JPEG 为 256 × 128。用系统 ImageIO 独立读取本机样本库的 HDR JPEG 和两张 ProRAW，三者的主图均为 8064 × 6048，且均带增益图。该尺寸下 A 的 8 B/像素扣款约 372.1 MiB。现有 JPEG 预览单项的全幅估算也为 372.1 MiB，超过剩余约 139.9 MiB，即使暂不扣窗口绘制及旧 B。 [便携夹具](../tests/data/portable-hdr/README.md) · [原生解码与缩略图](../src/qvcocoafunctions.mm) |
| 依据 | Apple 将缩略图长边限制定义为输出限制。编解码器不支持所请求的采样倍率时可能返回更大或全幅图像，因此预览仍为全幅中间图保留工作预算。 [ImageIO 缩略图尺寸](https://developer.apple.com/documentation/imageio/kcgimagesourcethumbnailmaxpixelsize) · [ImageIO 采样倍率](https://developer.apple.com/documentation/imageio/kcgimagesourcesubsamplefactor) |
| 推断 | 这种尺寸组合在原路径中先于像素解码被拒绝。限制缩略图输出尺寸本身无法使旧预检通过。分别检查输出可常驻的成本和全局解码工作量能消除这类拒绝。 |
| 未知 | 用户实际使用的文件、图像尺寸和窗口状态未提供。本次用可再生的大尺寸增益图 JPEG 建立回归证据。ImageIO、Core Image、Qt 与 Metal 的内部工作量依赖系统和编解码器，账面预算约束应用用于决定是否解码的估算。 |

## 设计与正确性论证

1. 原生探测同时返回最大图像尺寸和可预览的主图方向尺寸。预览支持 ImageIO 能识别的单图 JPEG、PNG、HEIF 及 RAW。JPEG、PNG 和 HEIF 要求单图容器。RAW 可含嵌入预览，沿用首图与缩略图路径使用的同一主图。Qt 的动画检查仍先执行。预检使用 Qt 与 ImageIO 尺寸中成本较大的一项。
2. 令窗口余量为 W，进程级候选图预留为 U，进程级上限为 C = 512 MiB。完整解码估算 F 必须同时满足 F ≤ W 和 U + F ≤ C。条件满足时优先读取完整图像，原生 HDR 仍进入原来的渲染路径。
3. 完整预留失败时，以不超过 1024 像素的边长解码 SDR 预览。窗口须能容纳预览的保守输出上界 R = 8 × edge² + 8 MiB，其中 edge 取主图长边和 1024 的较小值。预览解码的进程预留 P = max(Qt、ImageIO 全幅尺寸的 8 B/像素估算) + 编码字节 + R，须满足 U + P ≤ C。编码上限在两条路径之前校验。P 复用既有进程级预留，并允许小于 P 的窗口余量，只要 R ≤ W。解码期间 A 和窗口绘制的原有内存仍存在，故比较窗口的瞬时估算可超过 512 MiB。
4. 缩略图调用返回后，以两份实际栅格字节加固定开销计费，校验其未超过 R、再将全局预留由 P 缩减为实际保留量。于是替换前后的 B 同时存在时，窗口账面成本也在原预算内。预留通过共享所有权覆盖未提交结果及已提交图像。失败和取消按原生命周期释放，异步结果通过文件版本与请求编号检查后提交。预览携带方向校正后的主图尺寸，进入现有的缩放和 “SDR preview” 状态。

原子的全局加法在 C − U 内完成，成功后 U + P ≤ C 或 U + F ≤ C。预览的实际保留成本小于等于 R，R 又同时小于等于 W 和 P。缩减及释放只会降低 U。候选图失败时旧 B 继续持有自身预留，参考图及其原生 HDR 状态继续由原视口持有。无足够常驻余量、进程工作预留不足、格式不支持预览或解码失败的候选图仍可被拒绝。

# 退出双图后恢复拖动和 Z 键的技术设计

## 问题、前提与约束

按 Esc 退出双图后，参考图 A 继续在同一窗口显示，并恢复进入前的旋转、镜像、倍率、缩放模式和可见位置。手动视图超出可用画布时可拖动。Z 沿用单图的适合窗口／100% 切换，遵守应用设置。适合窗口后图片若完整可见，滚动范围自然为零。

**依据。** 双图退出保留加载中的视口 A，调用 `loadSessionState()` 后重算约束并恢复中心。现有恢复先设置只包含方向的单位倍率变换，随后调用 `zoomAbsolute()`。后者以 `requestedLevel == zoomLevel` 判定无需提交。Z 的判定同时读取保存倍率和滚动范围，拖动由已经应用的内容边界约束。 [退出流程](../src/qvcomparison.cpp) · [视口恢复与输入](../src/qvgraphicsview.cpp) · [Qt 视图变换](https://doc.qt.io/qt-6.11/qgraphicsview.html#setTransform)

**推断。** 当退出目标等于当前记录倍率且该倍率对应的渲染比例不同于单位比例时，提前返回会使记录倍率与实际画面比例分离。单位倍率可能把应可拖动的参考图缩进画布，从而没有滚动范围。也可能把应适合画布的参考图放到超出边界，使 Z 仍选择适合窗口，而得到相同数值并再次跳过提交。

**设计决策。** 恢复到已加载的视口时，在写入保存的图像方向后直接复用现有同步缩放事务，按保存倍率重建变换、场景边界和滚动范围，即使倍率字段相同。退出对比随后照常按实际单栏画布恢复适合模式或手动中心。开窗时还没有像素，沿用已有的延后图像布局路径。保持一次 Esc 退出、焦点归还和窗口级 Z 分发。

## 正确性论证与回溯

| 性质 | 推导与回查 |
| --- | --- |
| 已加载视口的变换一致 | 令 R 为保存的方向变换，z 为保存倍率，d 为当前视口的应用像素比例。恢复先安装 R，随后无条件执行同步缩放提交。既有事务在清理过时重采样后按 R × (z × d) 归一化变换和边界。当前倍率与 z 相等时也会写入正确几何。 |
| 拖动与 Z 恢复 | 场景和可见范围由同一变换重新生成。超出画布的轴恢复可用滚动区，鼠标通过单图拖动代码改变偏移。适合模式重新计算并更新滚动条，Z 依据实际适合状态决定到 100% 或适合窗口。 |
| 保存状态与生命周期 | 倍率真正变化时照常发布数值变更。保留方向、模式和视口中心的既有恢复顺序。不加载新文件，不增加异步步骤。比较视图的取消和销毁仍在恢复 A 前完成。 |

检索先定位 Esc、焦点和动作启用，再回查拖动边界与 Z 的几何判断，最后回溯恢复函数中的同倍率短路。测试分别覆盖同倍率／异倍率、超出画布时拖动、适合窗口时 Z 往返。

**回溯结果。** 基线动态用例确认同倍率恢复保留了错误的单位比例，拖动和 Z 两项也在基线失败。修复后的对应断言均通过。 [测试结果](test_completion_report.md)

**待验证。** 自动化覆盖本机 Cocoa 和当前系统缩放。其他 macOS／显示器组合的物理输入表现需对应环境。

# 双图分隔条与初始等宽修复设计

## 问题、前提与约束

双图模式的分隔条应沿左右窗格实际间隙的中线绘制。拖动预览跨过任一画布时，仍需在原生图像及其覆盖层前方可见。初次进入或双击重置时，两列平分扣除分隔条后的可用宽度，奇数个逻辑像素允许相差一个。保留非实时拖动，避免在每次指针移动时重新分配原生表面。用户提交的新分隔比例应延续到常规布局更新。

**依据。** 当前代码传给 QSplitter 的初始和重置尺寸均为 `{1, 1}`。Qt 会先将每项提升至该子控件的最小布局尺寸，再以结果计算比例。B 的列头包含选图和移除按钮，因此最低宽度可随文本和样式增大。默认非实时拖动的橡皮筋是 QWidget，而 Cocoa 的 SDR/HDR 层和导航层是顶级原生视图中的子层。Qt 的橡皮筋几何本身已按手柄宽度偏移。它的样式外观和被原生层覆盖是不同问题。 [Qt 分隔器实现](https://github.com/qt/qtbase/blob/v6.11.2/src/widgets/widgets/qsplitter.cpp) · [现有对比布局](../src/qvcomparison.cpp) · [原生图层挂载](../src/qvcocoafunctions.mm)

**设计决策。** 两列最小宽度统一为两者最低布局宽度的较大值。进入与双击重置用同一个函数，按扣除分隔器后的实际宽度设置等权的尺寸。把固定宽度手柄的中点用作静止分隔线中心。拖动用 Qt 的合法位置约束及最终移动接口，临时线画在候选手柄的同一中点，复用当前窗口的原生坐标变换，在根图层上显式使用高于图像与导航的层级。拖动期间只移动临时线，释放后一次提交；失去拖动归属、退出或窗口失活时同步撤掉临时线。 [Qt 手柄接口](https://doc.qt.io/qt-6.11/qsplitterhandle.html) · [Core Animation 层级](https://developer.apple.com/documentation/quartzcore/calayer/zposition)

## 正确性论证与回溯

| 性质 | 推导与回查 |
| --- | --- |
| 等宽可行 | 共同最小宽度为 M，设可分配宽度为 W。双栏窗口布局下 W ≥ 2M，因此 floor(W/2) 和 ceil(W/2) 均满足约束。两列最小宽度相同，输入等权且尺寸不低于 M 时，Qt 尺寸裁剪无法给两列制造不同权重。实际差值只来自整像素拆分。 |
| 中线一致 | 手柄宽为 H，左边界 X 等于左窗格的末端，右窗格起点为 X+H。中线为 X+H/2。拖动时把保存的按下偏移从指针位置扣除，获得候选左边界，通过 Qt 约束后加 H/2 绘制。释放使用同一个约束，所以预览和落位重合。 |
| 合成与生命周期 | 窗口根图层下的预览层顺序高于两侧原生层。拖过视图边界或另一图层稍后插入时，高层级仍决定覆盖顺序。释放或取消撤除临时层，原有 Qt 手柄恢复可见。测试查验实际根图层的附着和顺序。 |

先回查对比布局和 Qt 的尺寸裁剪，再定位橡皮筋的绘制层，最后用窄窗口、奇偶宽、偏心抓取、HDR 画布相交和拖动取消反向核验。

**待验证。** 本机执行 Cocoa 自动化并直接检查图层树。其他系统版本和外接 EDR 显示器的视觉表现需要对应硬件。

# 双图对比模式技术设计

## 问题、前提与约束

当前窗口只持有一张已提交图。目标是在同窗左右两列呈现参考图 A 和对比图 B，支持两个彼此独立的同步开关、独立缩放及左右交换。首版使用本地静态文件。A 继承原图状态，B 可选取、替换和移除。目录导航在对比期间暂停，退出恢复 A 原视图。功能约定以 [双图方案](design.md) 为准。

**依据。** 单图的缩放锚点、浮点平移约束、静态图解码、Qt 代理和原生色彩路径已存在。窗口遮挡计算目前绑定主视口，加载器前台实例只跟踪一个请求。Qt 调整已有分隔器子控件的顺序无需换父级。滑块的用户动作信号发生在默认值提交前，而滚动条值变化也会由布局触发。缩放读取可能先全尺寸解码。 [视口](../src/qvgraphicsview.cpp) · [平移](../src/scrollhelper.cpp) · [文件加载](../src/qvimageloader.cpp) · [Qt 分隔器](https://doc.qt.io/qt-6.11/qsplitter.html#insertWidget) · [Qt 滑块](https://doc.qt.io/qt-6.11/qabstractslider.html#actionTriggered) · [Qt 解码](https://doc.qt.io/qt-6.11/qimagereader.html#setScaledSize)

**设计。** 由窗口持有对比界面和稳定的 A/B 视口，A 从单图起就是分隔器子孙。同步入口只接收用户意图，按当前 A/B 状态计算两套局部更新。各列使用独立场景、缩放、滚动条和原生呈现实例。列头和控件位于画布外，显示活动身份、名称、倍率和加载反馈。按本列原点计算遮挡；分隔器拖动预示新位置，松手提交。菜单按活动窗口同步，非查看类单图命令暂停，Esc 先退出对比。

**加载和资源。** B 的预查和读取在全局串行对比队列执行，复用主图静态解码、版本和色彩能力。工作线程独立于窗口。先预查文件和源尺寸，对已知可计量路径保守估计，占用与旧 B 同时计入准入。完整路径预算不足时，具备已知尺寸的 JPEG 可采用原生受限 SDR 预览。预览保留原始定向尺寸，同时计入可能解码的全尺寸临时像素和缩小后的缓冲。候选若无可提交的完整像素或代理图，保留已提交的 B。候选有可呈现数据时一次提交 B 的身份、像素和适合状态；有命名代理的原生图随后提升画质。再次选择、移除、退出或关窗取消候选；替换期间旧 B 继续可查看。原生合成实际时点与可控资源之外的系统峰值可用实机观察。

## 正确性论证

| 性质 | 前提、推导与可观察结果 |
| --- | --- |
| 共同缩放与独立开关 | 对每个参与列，当前倍率 z 在其可用区间内，允许因子区间为 [lo/z, hi/z]，含 1。因此交集非空，限制到交集的同一正因子保证各列不越界且保持倍率比。独立模式参与集合只有源列。同步平移开关不介入锚点补偿。 |

| 相机与双交换 | 屏幕槽位只引用稳定的视口身份。交换是排列 (A,B)→(B,A)，执行两次为恒等。手动中心取自独立于布局投影的期望值，重排的裁剪不会改写它；相同视口几何下再次投影得到原构图，误差来自滚动整数化。交换只更新布局和已有内容变换。 |
| 最新结果与失败保留 | 每个候选携带请求身份和读前、读后匹配的文件版本。仅存活且最新的候选能提交，布局改变独立于请求。候选失败只更新提示，B 提交前无覆盖动作。退出使候选失效，迟到结果无法触及新的会话或已析构的窗口。 |
| 资源与线程 | I/O 在线程池，只有界面线程可提交控件。全局串行队列限制实际同时运行的比较读取。候选资源在准备前检查，取消后的同步读取仍占线程位置直到结束。已知缓冲按预算估计，系统编解码和 GPU 共享内存需实测校准。 |

## 迭代检索与回溯

先追踪窗口菜单、视口和已有加载入口，确认可以保留单图 A 和现有渲染器。再对读前后版本、平移约束及滑块信号回查，确定把程序化滚动与用户意图分开。最后以「选择 C → 交换 → 选择 D → C 完成 → 退出 → D 完成」、源轴到边缘、倍率饱和以及不等宽交换两次回查状态不变量。

# 修复文件重命名、图像缓存、URL 和磁盘预查

## 问题、前提与约束

审计基线为 `6c26ba4`。Cocoa 下已复现同路径替换导致重命名操作错文件、BMP 和 EPS 返回旧像素，以及重定向后的 PNG 被当作 EPS。打开、导航和预读计划同步查询文件系统是源码事实。慢卷会把这些调用的等待传给界面线程是由调用边界得出的推断，真实 SMB 与离线卷耗时未知。

复用已有主图和缩略图工作队列、缓存容量、导航边界、最近文件和下载租约。直接打开文件、文件夹、目录内切图、缩略图点击、显式重新加载以及动画均保留既有界面语义。文件版本以操作系统可见的元数据为依据。

| 问题 | 设计 | 正确性论证 |
| --- | --- | --- |
| 重命名目标改变 | 对话框记录打开时目录项的元数据版本。只在用户确认修改时尝试操作，紧邻重命名再核对，符号链接按链接本身验证。 | 设备号、inode、大小和高精度 mtime、ctime 共同标记目录项。移走、覆盖、修改或移除原目录项都会使版本不同或不可读。此时不重命名、不发出打开新文件信号。正常命名仍沿用 Qt 的名称冲突处理。 |
| 主图和 EPS 缓存过期 | 主图工作线程读前、读后取同一版本。普通缓存命中也在工作线程复核版本，显式重载绕过普通主图缓存。EPS 渲染缓存加入源和渲染器版本，渲染结果只在当前版本下存入。 | 原子替换即使保留大小和 mtime，也会改变 inode 或 ctime。普通请求发现版本不符就实际解码。读取期间版本变化会撤销该次结果并按当前需求重试。缩略图携带预期版本时继续按原契约拒绝变化。同一版本仍可复用，EPS 的内层缓存也无法命中新版本的旧像素。 |

| 打开及导航同步预查 | 在前台工作池对直接输入做文件与目录分类。方向和边界仍由内存目录快照计算，逐项跳过已消失邻居的查询在前台工作池执行。预读需求在界面线程只维护路径与优先级，其缓存和文件元数据由工作任务读取。目录监听使用扫描产生的物理根路径，窗口标题使用已加载图像的元数据快照。 | 慢文件系统预查只能占用工作线程，界面仍处理输入和绘制。每窗口仅接受一个路径解析结果，显式打开、关闭或销毁取消旧票据。未找到邻居时保持当前画面，越界即时反馈，已找到邻居仍进入同一个主图加载入口。把快照和源租约交给工作任务可以在取消后安全释放文件。 |

POSIX 重命名按路径执行，源码版本核对与系统调用之间依然存在很窄的并发窗口。平台没有为源目录项提供按 inode 比较并重命名的原子接口。主图读取和缓存复验以工作线程最后一次有效观察为准，之后的外部写入由下一次读取识别。慢盘修复的范围是审计列出的文件类型、导航存在性、缓存版本、标题元数据和目录监听根预查。最近文件审计、备用路径别名匹配、信息面板和动画读取的慢卷耗时未纳入本次验收。

# SVG 拖动性能修复设计

指定的 `sdr_test/7.svg` 含 10,804 字节，声明宽度 119.66407、高度 40，原始视框为 `0 0 119.66407 40`。加载器保留规范化 SVG 和缩略预览，worker 以缓存的原始视框独立栅格化每个瓦片。原生 2× 全屏拖动基线在 44.3146× 缩放下记录了 43 次完整绘制，43 次均命中缓存并启用平滑重采样；中位数 5.77 ms，p95 6.95 ms。少一个设备像素的比例误差就足以让原有一对一检查失败。跨越瓦片时，原 SVG 路径还会把整幅预览画在透明瓦片下方。 [Qt QSvgRenderer](https://doc.qt.io/qt-6/qsvgrenderer.html) · [Qt SVG 视框映射实现](https://github.com/qt/qtsvg/blob/6.10/src/svg/qsvgtinydocument.cpp)

## 设计与正确性论证

1. 将 EPS 已验证的整数设备坐标请求与复制路径用于所有有效矢量图元。对于正向轴对齐的可逆变换 T，设备矩形 D 为 T(R) 的整数外包矩形。按 D 的整数宽高栅格化逆映射 T⁻¹(D)，瓦片比例等于当前设备比例。平移整数物理像素后，瓦片与屏幕像素仍一一对应，完整覆盖与局部覆盖均可直接复制。通过现有对齐谓词校验实际位图、比例与像素相位；旋转、镜像、相位不匹配与预算降采样继续经过过滤。
2. 令 B 为原始 SVG 视框，L 为图元逻辑尺寸，R′ 为贴齐后的瓦片源矩形。现有映射把图元坐标 x 对应到 SVG 坐标 B.left + x × B.width / L.width，纵轴同理。用该映射计算 R′ 的 SVG 视框，再将其映射到瓦片位图。对于一个 SVG 点，无论直接渲染完整图元再裁切，还是用瓦片视框渲染，得到的像素位置均是 (x − R′.left) × D.width / R′.width。边缘瓦片先将文档内的 R′ 交集映射为位图裁剪区，避免一像素外扩让页外绘图指令进入瓦片。每次使用缓存的原始视框计算，支持无显式视框的 SVG。
3. 将 EPS 的局部预览裁剪用于 SVG。令视口需绘制区域为 E，所用瓦片覆盖区域为 C。背景先覆盖 E，预览覆盖 E ∖ C，图块覆盖 E ∩ C，透明瓦片仅与背景合成。完整重绘模式、终止时的细化、动画世代判断、显示色转换与既有内存和任务队列预算沿用原路径。
4. 首次实现只消除了重采样，三轮原生对照的 p50 与 p95 均没有下降。Qt Cocoa backing store 和 worker 输出都使用预乘 ARGB32。worker 在显示色转换后对 SVG 瓦片检查所有 Alpha 字节。仅在一对一复制、当前画笔为全不透明 SourceOver 且瓦片 Alpha 恒为 255 时，改用 Source。因为在此条件下 SourceOver(S,D) = S，两种合成等价，Qt 可直接复制。若该瓦片同时完全覆盖需绘制的区域，则其中的图元背景填充会被逐像素覆盖，可省去这一遍填充。透明、部分覆盖、低画笔不透明度等情况仍按原合成条件处理。Alpha 检查随异步栅格化做一次，交互绘制直接读取结果。 [Qt raster engine](https://github.com/qt/qtbase/blob/6.10/src/gui/painting/qpaintengine_raster.cpp)
5. 用有偏移的 SVG 视框、无显式视框、旋转、透明跨界和指定样本分别核验几何与拖动。用同一 Release 基线和候选构建重复原生比较，降低单次测量的波动。

# EPS 拖动性能修复设计

指定的 `6.eps` 是 DOS EPS，含 4,085,128 字节的 PostScript 正文和 11,666 字节的 TIFF 预览，边界为 120 × 40 点。Fovelle 的 Ghostscript 路径把正文转换成 PDF；可见图元从该 PDF 异步生成显示密度瓦片，再把预乘 ARGB32 瓦片交给 QPainter。普通 SDR 图片可用独立的原生合成路径。

原生全屏拖动在 2× 屏、43.9453× 缩放下记录到尺寸为 3681 × 2393 的图块。可见区域为 1711 × 1067 逻辑像素，预期内部图块宽度为 3422 + 2 + 256 = 3680。连续绘制即使报告缓存命中，仍进入双线性采样；经过图块边缘时，旧图块局部覆盖，而原实现先对整个视口放大预览，再叠画旧图块。旧 CPU 探针未等待起始高密度瓦片发布，并在两像素内往复，不能代表持续拖动。Qt 的绘图文档和 raster engine 实现均表明，对齐的一对一图像复制可走不需要重采样的路径。 [Qt QPainter](https://doc.qt.io/qt-6/qpainter.html) · [Qt raster engine](https://codebrowser.dev/qt6/qtbase/src/gui/painting/qpaintengine_raster.cpp.html)

## 设计

1. 对正向、轴对齐的 PDF 瓦片，把请求边界在设备空间向外贴齐整数像素，并用整数包围盒尺寸栅格化。若贴齐后超出既有像素或边长预算，沿用原有有界瓦片。旋转、镜像和发生像素相位变化的绘制继续支持平滑采样。
2. 允许 PDF 图块在文档边界保留不足一设备像素的透明外边距。Core Graphics 以请求矩形建立坐标映射，再裁剪到实际 PDF 页面。整份文件始终保留权威 PDF，现有颜色转换、异步代际检查与缓存上限继续生效。
3. 可重用瓦片的几何范围与当前变换都符合一对一整数像素条件时，缓存命中和同密度局部重用使用相同的复制路径。只在瓦片未覆盖的区域绘制预览；图块覆盖下的透明像素直接显露纯色或棋盘格背景。保留交互期间全视口重绘与释放后的异步细化。
4. 验收同时使用确定性透明 EPS、同尺度栅格参考和指定 EPS。性能比较记录 GUI 线程 CPU 时间及事件路径，原生 HID 检查验证真实 bundle 的全屏拖动和退出位置。

## 正确性论证

设正向设备映射为 T(x) = sx + t，s > 0。对请求区间 [a,b]，取整数设备边界 L = floor(T(a))、R = ceil(T(b))，并把 [L,R] 逆映射回文档。它包含原区间，输出宽度 R−L 恰为映射的物理像素数。纵轴同理。页面裁剪在该映射下限制 PDF 内容，超出页面的像素保持透明，边缘附近也无需为凑整而改变比例。设备映射未变或仅有整数像素平移时，图块每一像素依然与目标像素一对一；相位、采样密度或轴方向不符时使用过滤绘制。浮点计算仅在贴近整数时吸收舍入误差。

令 E 为本帧需显示的文档内区域，C 为所用图块覆盖区域。背景先覆盖 E，预览仅画在 E ∖ C，图块画在 E ∩ C。两区互斥且并集为 E，因此图块透明像素不会混入预览。无图块时预览覆盖 E，有完整图块时只画图块。每个图块仍先经过像素及边长预算，异步请求仍由最多一个活动任务和一个替换请求管理。滚动值、拖动位置与释放后的细化均使用现有事件路径。

# 大 TIFF 缩略图修复设计

## 核心问题

导航条会为尚未打开的邻居图像异步解码缩略图。原始样本 `141 Jaguar Attacking a Horse - Henri Rousseau 1910.tif` 位于本地挂载盘，首帧为 11409 × 8705、8 位 CMYK、LZW 条带 TIFF，共 99,315,345 像素、456,039,220 字节。当前原生缩略图先因编码大小超过 256 MiB 退出。即使只放开该条件，64,000,000 像素门槛也会拒绝该图。Qt 通用回退还有 64 MiB 编码大小和更低的像素门槛。ImageIO 独立探针在绕过 Fovelle 准入后返回 256 × 196；一次实测峰值 RSS 为 497,303,552 字节。Apple 文档允许 ImageIO 忽略子采样请求并使用完整源图，因此独立像素预算仍有必要。 [Apple ImageIO 子采样](https://developer.apple.com/documentation/imageio/kcgimagesourcesubsamplefactor)

## 设计方案

1. 在原有 PNG 分流之后判断是否超出 256 MiB。超出时，仅允许 512 MiB 内、头四字节符合 TIFF 或 BigTIFF 签名的文件交给 ImageIO 识别，并关闭 Qt 回退。ImageIO 必须确认类型为 `public.tiff`，然后才允许这个文件进入缩略图解码。TIFF 签名也可能属于 DNG 等格式，因此签名只是读元数据的预筛选。
2. 由编码大小或像素数触发 TIFF 独立预算。只有正尺寸、单边至多 32768、总像素至多 1 亿、ImageIO 报告 8 位非浮点 RGB、灰阶或 CMYK 的首帧才可解码。小 TIFF 延用原路径。512 MiB 是编码输入上限，1 亿和单边上限约束源图工作量。允许的 8 位、至多四个颜色通道及 RGB 透明度对应的典型 4 字节像素表面约为 400 MB，ImageIO 内部缓存、转换和文件映射可另外占用内存。保留全局串行解码锁，不对 ImageIO 的瞬时内存作硬上限承诺。
3. 大 TIFF 使用已有 ImageIO 缩略图路径生成 SDR 图，继续由导航条执行最终包围盒缩放、颜色归一化和预乘。读取首帧并由 ImageIO 应用 TIFF 方向。沿用本地文件读取检查、后台队列、版本校验和失败占位。部署依赖仍为已有系统框架。
4. 排查同目录真实图片和既有 SDR、HDR、混合样本。跳过 macOS `._` 伴生文件。GALLERY 的头部普查显示 149 张 PNG、3 张 JPEG 和 1 张 TIFF；其中 43 张 PNG 超 256 MiB，均在现有流式 PNG 硬上限内。对最大编码 PNG 和最大像素 PNG 实际运行导航条，区分预算内但耗时的文件和返回空图的故障。

## 正确性论证

令 B 表示编码字节数，P 表示通过元数据取得的首帧像素数。非 TIFF 在 B 超出通用阈值时无法通过签名和类型的双重条件；B 在通用阈值内时保持各格式原有像素和回退策略。PNG 在文件门槛前已有独立处理。对普通 TIFF，B、P 均在旧预算内时继续使用相同的 ImageIO 缩略图配置。对其余 TIFF，原生像素解码前必须同时满足独立预算和 8 位格式条件；任意条件缺失时，返回占位且不启用 Qt 回退。宽高乘积用 64 位运算。原图的 B、P、每边尺寸和颜色格式均满足独立预算，探针也证实了其 ImageIO 解码能力。

导航条调度在 GUI 之外，且进程内最多执行一个缩略图解码；过期文件版本、失效订阅和缓存仍由同一发布路径处理。ImageIO 返回的尺寸无论是否执行子采样，都经已有输出约束归一化，因此实际预览无法超出槽位的物理像素范围。

# 默认适合窗口的双滚动条修复

## 核心问题

打开用户提供的 JPEG 后，默认的「适合窗口」应完整显示图片。原图为 3456 × 1968 像素，144 DPI，无 EXIF 方向标记。决定是否滚动的是解码后的像素尺寸、当前视口尺寸与标题栏遮挡区域。

加载链路从 `MainWindow::openFile` 到 `QVGraphicsView::postLoad`，再经 `fitOrConstrainImage` 和 `recalculateZoom` 提交缩放与场景矩形。原算法在两个取整后的轴尺寸看似都能填满视口时会选择较大比例。以 642 × 365 DIP 的可用区域为例，宽度决定的比例会得到 642 × 365.58333 DIP。Retina 的逻辑像素取整可能把高度记作 365，但 Qt 根据浮点场景范围先判断纵向溢出，再从可用宽度扣减竖条宽度，随后建立横向范围。 [Qt 场景与滚动范围计算](https://codebrowser.dev/qt6/qtbase/src/widgets/graphicsview/qgraphicsview.cpp.html#344)

## 设计

- 统一自动重新适配与「适合窗口 / 100%」切换的目标计算。适合窗口取两个浮点尺寸比例中的较小值，边界向内保留几个机器精度单位。可用尺寸仍取无自动滚动条的视口，并扣除原生标题栏遮挡。
- 对使用高质量重采样的 Qt 栅格图，最终背板的整数物理像素可能向上取整。适合窗口时，用同一个上界再限制实际背板变换。手动缩放、填满窗口和原始大小继续遵循既有规则。
- 保留小图 1:1 偏好、适配缩放上限、全局缩放上下限和历史 overscan 设置。无滚动条的承诺适用于默认零 overscan，且所需缩放在受支持的范围内。

## 正确性论证

令旋转及显示 DPI 换算后的图像尺寸为 `w × h`，无条视口的可用尺寸为 `W × H`。取 `s ≤ min(W/w, H/h)`，因尺寸为正，必得 `sw ≤ W`、`sh ≤ H`。使用小于 1 的机器精度因子给浮点除法、乘法及场景补偿留出舍入余量。允许 1:1 的小图分支已经要求两轴都严格小于可用尺寸。适配上限只能继续缩小结果。

原生标题栏遮挡高度为 `T` 时，屏幕纵轴最多追加 `T`，所以适配后的场景高度至多为 `H+T`，宽度至多为 `W`。两轴均在 Qt 用来判断溢出的无条视口内，因此不会触发相互挤占。对重采样后得到的背板重复同一不等式，防止整数背板恢复范围。手动放大后仍由 Qt 按实际内容范围显示滚动条。

# 缩略图键盘跨可见边缘导航设计

## 核心问题

`focusStrip()` 将键盘焦点放在当前主图对应的缩略图上。应用事件过滤器接管左右键，但原有处理只扫描 `visibleCells` 中与 `cellClip()` 相交的槽位。该状态只描述面板当前画了什么。图像目录仍有前一项或后一项时，扫描也可能在槽位边缘耗尽。

## 设计

- 以键盘焦点对应的目录索引为起点，左键减一，右键加一。沿用目录循环设置。关闭循环时，实际首末项的外向按键被缩略图栏消费，焦点和浏览位置保持原值。开启循环时，首项左移到末项，末项右移到首项。
- 列表就绪时，在已绘制槽位中按目标目录索引查找与裁切区域相交的项。若目标可见，直接移动焦点。否则结束旧的切图过渡，清除旧鼠标按下槽位记录，把浏览位置移到目标并重建槽位，使目标居中。随后按目标索引重新查找槽位，并刷新焦点、预览、指针命中和无障碍按钮。
- 回车、小键盘回车和空格继续通过 `activate(focusSlot)` 确认。该路径通过同一快照检查目录索引、路径和文件版本，加载成功后由原有提交逻辑更新主图。Escape 继续关闭面板。

## 正确性论证

1. 列表就绪时，设焦点目录索引为 `i`，列表大小为 `n`，方向为 `d ∈ {-1, 1}`。对合法的 `i + d`，一步恰好到达目录邻项。越界时，关闭循环则保持 `i`，开启循环则将结果按 `n` 回绕。因而可见槽位数量、空槽和目录循环布局不能让按键跳过合法邻项。
2. 可见目标直接取得焦点。对屏外目标 `j`，现有 `layout()` 在整数浏览位置 `j` 的中心槽放置 `j`，该槽处于裁切区域内。重建后按 `j` 查找并设置焦点，避免把重建前的槽位编号当作目标。下一次按键从新焦点的目录索引出发。以当前主图的初始焦点为基例，重复按键可按顺序遍历整个目录。
3. 移动焦点的调用链只更新缩略图视图状态。确认键才把新焦点的槽位交给 `activate()`。该槽位的目录索引和路径来自同次布局，原有异步校验还会拒绝过期列表或文件版本。因此跨边缘后确认的是新目标，方向键本身不会提交主图。

# 长截图与 RAW 缩略图方向修复

## 根因

FireShot PNG 为 3352 × 24126、8 位，合计 80,870,352 像素。在后台调用 ImageIO 前即被 6,400 万像素门槛拒绝。独立 ImageIO 探针以 8 倍子采样成功生成 40 × 288 的完整预览。

Sony ARW 的 ImageIO 方向为 EXIF 8，主图为竖向，`CIRAWFilter.previewImage` 却返回横向。Nikon NEF 的 ImageIO 方向为 EXIF 1，主图为横向，内嵌预览却为竖向。两者的 RAW 草稿输出应用同一方向后，与完整 RAW 图像按像素布局比较均一致。内嵌预览是单独的相机图像，调整 `filter.orientation` 无法为它建立与 RAW 解码图相同的方向约定。 [Apple RAW 预览](https://developer.apple.com/documentation/coreimage/cirawfilter/previewimage?language=objc)

## 设计与正确性论证

1. 保留现有通用栅格门槛。在 PNG 确认可请求 8 倍子采样、样本深度可确认且为 1–8 位时，允许最多 1 亿源像素。按最宽 RGBA8 表示估计，源像素缓冲上限为 400 MB。子采样和最终缩略图尺寸约束继续生效。该分支只增加符合条件的 PNG，JPEG、HEIF、TIFF、RAW 和 Qt 回退的上限沿用原值。 [Apple ImageIO 子采样选项](https://developer.apple.com/documentation/imageio/kcgimagesourcesubsamplefactor)
2. RAW 缩略图和主图都从相同 ImageIO 方向配置 `CIRAWFilter`，使用 RAW 解码图的 `outputImage`。缩略图先用草稿模式和原有目标比例，草稿无法输出时在相同比例下尝试普通模式。两个分支均从传感器图解码并应用同一个 EXIF 方向。缩放只改变取样大小，因此不会引入额外的旋转或镜像。相机内嵌预览不再用于缩略图方向判断。
3. 使用原有后台队列、文件版本校验及缩略图输出边界。若 RAW 解码图在两种模式均不可用，保留占位，避免展示方向无法确认的内嵌图。主图的解码、HDR、转场和切图入口保持原状。

# 缩略图切换过渡与横向浏览

## 设计

当前缩略图状态直接从已提交的目录索引重建。切图时旧画面随重建被替换，滚轮和触控板事件则继续进入主图的导航或平移。新增独立的浏览位置，范围为目录首末索引，支持小数位置。鼠标滚轮每 120 角度单位移动一格，触控板优先使用像素增量。常规双指滚动走 Qt 滚轮事件，原生横移和左右滑动也可浏览。滚动在已显示面板内起始时由缩略图条消费，带阶段的滚动在手势停顿时保留归属，结束后继续接收惯性，边界上的剩余增量同样消费。面板外起始的序列沿用视口映射。 [Qt 滚轮事件](https://doc.qt.io/qt-6/qwheelevent.html) · [Qt 原生手势](https://doc.qt.io/qt-6/qnativegestureevent.html)

横向浏览按目录顺序平移，可让当前图离开可见范围。槽位、绘制、点击和无障碍元素共享裁切矩形。滚动只修改浏览位置和预览需求。点击、键盘确认或原有主图导航提交新文件时，才更新当前项并重新居中。再次打开条时从当前项开始。预览仍受可见窗口大小和原有解码预算约束。

同一目录内成功切图后，旧面板与新面板做 180 ms 交叉淡入淡出。Qt 绘制和原生合成使用相同进度，原生层只上传两端内容，逐帧更新透明度。快速切图从当时的合成画面续接，窗口尺寸变化时旧画面重新对齐新面板并保留进度。切换目录、关闭面板和系统减少动态效果时直接更新。过渡期间暂停缩略图激活，确保可点击图像与显示内容对应。滚动可立即结束过渡并接管浏览位置。

## 正确性论证

1. 当前项取自已经提交的主图。滚动处理只调整浏览位置，并在面板内接收事件，因此滚轮不会触发主图导航、缩放或平移。滚动到端点仍由原所有者处理。
2. 横向位置变化只在有限的相邻槽位上重建布局，跨槽时补充进入裁切范围的边缘图。超出目录范围的增量被截断。相同绑定沿用已有预览，异步结果仍按原代次核对。无障碍坐标和点击范围来自绘制使用的裁切结果。
3. 交叉过渡只在已成功提交且与旧图不同的同目录文件上启动。结束时只留下新面板，中心格重新指向已提交项。重新切换时先截取当前合成状态，再替换目标，关闭或减少动态效果时释放旧画面。

# 缩略图内容与尺寸修复

## 根因

缩略图工作线程先使用 Qt 识别格式，再经过窄格式名单和共用像素上限，之后才有机会调用 ImageIO。`64 MiB ÷ 16 B` 实际只放行约 419 万像素。常见相机 JPEG、较大的 PNG 和 Qt 无法识别的原生格式因此提前返回占位。RAW 与 EPS 的主图读取已有独立路径，旧缩略图入口没有接入这些能力。SVG 的逻辑画布也被当作栅格源计费。

## 设计

- 对已允许读取内容的本地文件，先走原生缩略图入口。ImageIO 依据自身类型与尺寸决定是否生成 SDR 缩略图。JPEG、HEIF、PNG、TIFF 可在 6,400 万源像素上限内请求原生子采样，其余普通原生格式上限为 800 万像素。RAW 在 6,400 万源像素内优先使用 Core Image 可提供的相机预览，否则使用按目标尺寸缩放的 SDR 草稿处理。EPS 输入上限为 16 MiB，复用既有受限 Ghostscript 转换及 PDF 栅格化，仅保留缩略图像素。 [Apple ImageIO 子采样](https://developer.apple.com/documentation/imageio/kcgimagesourcesubsamplefactor) · [Apple RAW 预览](https://developer.apple.com/documentation/coreimage/cirawfilter/previewimage?language=objc)
- 本地预览文件上限为 256 MiB。普通原生路径未得到图像时，由 Qt 已安装的读取器在 64 MiB 文件和 64 MiB 栅格估算开销的限制内回退。小体积 SVG/SVGZ 通过可缩放读取器直接按目标尺寸栅格化。保持文件版本校验、本地文件访问策略、串行解码、LRU 字节预算和 sRGB 输出。损坏或超出各自预算的图片仍可显示占位。
- 标准格从 72 × 52 pt 调整为 144 × 104 pt，紧凑格从 56 × 40 pt 调整为 112 × 80 pt。间距、边距、触发区和淡入淡出沿用原值。三格对称宽度门槛分别为 488 pt 和 392 pt。9 格标准预览在 2× DPR 下的像素数据为 2,106 KiB，仍计入现有 24 MiB LRU。较窄窗口按原规则减少槽位或隐藏。

## 正确性论证

1. 原生判定先于 Qt 判定。Qt 未注册读取器或旧的 419 万像素上限都无法拦截独立预算内的原生预览。原生失败时才进入 Qt 回退，Qt 回退在读取像素前仍检查源大小。
2. RAW、EPS 和 SVG 分支分别依据各自的输入与输出边界工作。每个成功结果仍按实际格宽高和 DPR 做最终等比缩放和边界检查，超限、读失败和版本不一致的结果不会进入当前槽。前台切图路径及现有加载器不受影响。
3. 对半径 r 的布局，宽度需求为 `(2r+1)×格宽 + 2r×8 + 40`。半径为 1 时得到 488 和 392。中心槽的偏移恒为零，减少可见槽位后中心仍与视口对齐。绘制和点击继续使用同一格矩形。

# 视口底部缩略图条技术设计

## 范围与接口

以 [交互设计](design.md) 为产品依据。每窗口的 `QVThumbnailStrip` 持有槽位、显隐、按压、焦点和文件请求状态。它使用 `QVGraphicsView` 的视口坐标，不参与主图布局。一个不接收鼠标事件的子控件负责 Qt 绘制。原生渲染器在现有导航覆盖层内持有单独的缩略图图层，复用同一幅带 DPR 的面板图像及同一透明度；面板内容变化时才重新生成图像。

核心负责发布目录失效和读取开始，提供按目录版本、当前文件、索引和路径校验的打开入口。悬停时使用核心目录列表的可见片段。接受鼠标释放或键盘激活后，在后台比对目标版本。待校验请求被后续打开、列表失效或窗口关闭撤销。主图继续沿用现有加载、缩放、错误与最近打开记录。显式悬停偏好通过 SettingsManager 持久化；仅改变悬停时不影响目录扫描和主图预读。

缩略图工作使用 Shared 队列，限制并发、合并同键需求，并在后台校验文件版本。LRU 按 QImage 实际字节计费。生产路径先使用可控的 ImageIO 或 Qt 解码，限制输出及全图解码预算，格式无法在预算内生成时显示占位。激活使用原始目录项路径，预览失败仍可尝试打开。主图版本受约束的读取在 Foreground 队列中校验读取前后身份；变化结果单独返回，由核心结束等待并保留已提交图像。

## 实现约定

- 原生路径为整个缩略图条保留一层已栅格化内容，悬停反馈或图片就绪时更新内容，透明度动画只改层透明度。Qt 路径重用相同的面板图像。
- 鼠标点击的校验有 800 ms 界面等待上限。过期回调丢弃，已进入同步系统调用的任务在调用返回前仍占用名额。
- 前台加载器为正常读入的缓存结果记录读取前后一致的文件身份。缩略图打开复用匹配的结果前，仍在后台确认当前文件版本。
- 悬停偏好走独立设置通知，目录过滤、排序、循环和主图设置沿用已有通知。原生菜单跟踪及辅助显示选项通过 Cocoa 通知同步。
- 不能在预览预算内生成的文件可显示格式占位。当前图可复用尺寸受限的已加载代理，邻居的占位仍可作为普通打开入口。

## 正确性论证

1. 当前索引来自已提交的 FileDetails。中心槽的偏移恒为零。越界和去重只作用于邻居槽。屏幕、窗口、滚动条变化重新生成同一个绘制和命中布局，覆盖层本身不改变主图几何。
2. 显隐转换仅修改覆盖层状态和透明度。进入与离开分别使用单次计时器，反转从当前透明度开始。关闭、阻止和退场时取消激活。按压所有权与激活资格独立，撤销资格后仍消费原序列的释放。
3. 每个激活携带目录版本、目标索引和原始路径。接受校验结果时再验证窗口、版本和当前项；在主图读取边界复验文件版本。失效结果无法更新当前项。主图只在核心提交有效结果时更换，缩略图异步回调只替换匹配的槽位图像。
4. 预览只提交可见需求。取消订阅不会增加正在运行的任务名额。QvAsync 的退出边界清理队列，窗口回调由弱引用保护。全尺寸读取前先检查源尺寸和估计缓冲，格式降级不改变槽位及导航目标。
5. 菜单、鼠标和键盘共享激活逻辑。Qt 与原生绘制共享布局和无障碍代理；切换渲染路径时关闭旧绘制并同步新绘制。键盘焦点存在时局部处理方向键、确认键和 Esc，退出后还给视口。

# 图片导航到达边界时保留缩放

## 问题界定

请求上一张或下一张时，如果目标仍是当前图片，视图应保留当前缩放比例和缩放模式。只有切换到另一张图片时才应用用户的导航缩放设置。

1. 菜单、悬浮按钮和键盘等入口最终调用 `QVGraphicsView::goToFile()`，由 `QVImageCore::goToFile()` 选择目标。
2. `FileDetails::updateLoadedIndexInFolder()` 先筛选规范化后大小写等价的路径，再用 `QFileInfo` 确认匹配。因此，已打开路径和目录枚举路径的字符串可以不同，文件索引仍然有效。
3. 关闭循环时，首张请求上一张或末张请求下一张会设置 `reachedEnd`，但仍继续处理当前索引。开启循环的单图目录也会选回当前索引。原有字符串判重可以被同一文件的不同路径拼写绕过，从而把当前图片交回加载器。
4. 加载结果触发 `fileChanging` 和 `fileChanged`，视图在 `postLoad()` 中根据 `navresetszoom` 应用默认缩放。这是切图时的正常行为。

## 设计

在 `QVImageCore::goToFile()` 中，关闭循环且到达边界时立即返回已设置 `reachedEnd` 的结果。完成候选索引查找后，如果候选索引等于当前文件索引且当前文件路径非空，也直接返回。保留现有的候选文件存在性检查。缩放设置继续由视图在加载时处理。

## 正确性证明

1. 首张请求上一张和末张请求下一张在关闭循环时都设置 `reachedEnd`。返回发生在查找和加载之前，因此两种请求均无法发起新加载。返回值继续驱动方向提示和幻灯片停止逻辑。
2. 开启循环时，单图目录的首末索引均为 0。两个方向都会选中当前索引。判重以索引为准，路径拼写差异不影响结果。`closeImage(true)` 可以保留目录索引，但会清空当前文件路径，所以同索引保护仍允许从保留的目录打开文件。
3. 以上两条返回路径都不会执行 `loadFile()`，因此不会发出由该次请求引起的文件切换信号，也不会触发 `postLoad()` 中的缩放更新。
4. 对于存在且索引不同的目标，包括多图目录中的循环切换，两个返回条件均不成立。目标沿原加载路径完成切换，继续按 `navresetszoom` 选择重置或保留缩放。

# WebP 与超大 PNG 缩略图修复

## 问题界定

验收对象是缩略图条中尚未打开的邻居项。测试必须等待后台预览提交，防止主图代理掩盖缩略图失败。生产调用链为 `QVThumbnailStrip::requestPreviews` → Shared 工作队列 → `readPreview` → ImageIO 或 Qt → 槽位及覆盖层。

- `5.webp` 为 4275 × 2451 的 VP8 WebP，共 10,478,025 像素。ImageIO 识别为 `org.webmproject.webp`，直接请求可返回 288 × 165 的预览。原生通用格式的 800 万像素上限提前返回，Qt 的约 419 万像素回退上限也拒绝此图。
- `9.png` 为 23,094 × 31,390 的非隔行 RGB8 PNG，共 724,920,660 像素，文件大小 1,385,269,031 字节。外层 256 MiB 上限已拒绝该文件，原生 PNG 的 1 亿像素例外也不足。强制 ImageIO 做 8 倍子采样可生成预览，但独立探针在本机记录到约 1.42 GB 峰值 RSS。 [Apple ImageIO 子采样选项](https://developer.apple.com/documentation/imageio/kcgimagesourcesubsamplefactor)
- 同级截图样本中的 `macOS 2.webp` 为 6016 × 6016，共 36,192,256 像素，命中同一 WebP 问题。覆盖 SDR、HDR、混合目录和截图样本，检查其他格式的邻居预览。

## 设计方案

1. 保留可读取性、文件身份、串行解码和输出归一化逻辑。在原生缩略图入口集中执行常规文件大小上限，并为超过 6400 万像素或 256 MiB 的 PNG 设置专用流式路径。按文件签名和 IHDR 尺寸分流，专用路径有 2 GiB 文件、10 亿像素、65,536 单边像素上限。专用解码被拒绝或失败时保留占位。
2. ImageIO 实际识别为 WebP 时使用独立的 4000 万像素上限，先检查元数据再调用现有缩略图转换，保留方向、透明度和 SDR 色彩处理。WebP 不请求 ImageIO 不支持的子采样。对 ImageIO 识别但无法返回尺寸的单块无损 VP8L，先核对 RIFF 头与文件边界，再用 libwebp 在同一像素上限及 64 MiB 文件上限内直接生成缩放图。其他格式沿用各自的上限。
3. 用 libpng 逐行处理大 PNG。支持低位深、调色板、灰阶、RGB、透明度和 16 位通道，归一为 RGBA8。对 Adam7 按各 pass 的实际坐标处理，采样到每轴最多为目标 4 倍的中间图。读完数据和 IEND 后，在预览尺寸上应用 EXIF 方向，再平滑缩小。保留适用的 ICC、sRGB、gAMA、cHRM 和已知 SDR cICP。专用路径遇到不能正确解释的 cICP 时保留占位。
4. 依赖采用经 SHA-256 校验的 libpng 与 libwebp 源码静态编译，使用项目已有的 zlib。qmake 通过 pkg-config 获取两者。测试与应用共用专用解码器。

## 正确性论证

1. WebP 由实际 UTI 判定。两张已知 WebP 的像素数分别为 10,478,025 和 36,192,256，均落在独立上限内。该分支复用已在原图上返回正确比例的 ImageIO 接口。超过上限的 WebP 无法进入原生像素解码。单块 VP8L 的回退只接受完整且无扩展块的 RIFF，因此不会忽略 ICC 或 EXIF 元数据。回退以解码器返回的真实尺寸执行同一个像素检查。
2. PNG 签名及 IHDR 将 `9.png` 送入专用路径，文件、面积和单边都满足其上限。libpng 再独立校验尺寸及数据，读完才交付。损坏或中断只能返回空图。常规大小的 PNG 仍由原有解码器处理。
3. 每个中间像素按像素中心映射到一个源坐标。非隔行图每行一次，Adam7 的 7 个 pass 划分全部源坐标且互斥，因此每个目标像素恰好得到一次填充。中间图存储量与目标尺寸成正比，行缓冲随源宽增长。元数据分配和源尺寸分别受限，没有随源面积或文件大小分配的输入或像素缓冲。平滑缩放在预乘 alpha 后进行，输出保留宽高比、方向和透明度。 [libpng 手册](https://github.com/pnggroup/libpng/blob/v1.6.59/libpng-manual.txt)
4. 两条路径均受现有后台解码锁控制。读前、读后的文件版本和槽位请求代次仍决定结果能否缓存或提交。临时失败、过预算和取消仍允许槽位作为导航目标。
